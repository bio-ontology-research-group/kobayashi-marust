# Exact native data values (v1.5.5, branch `fix/v155-native-data-values`)

Agent `data-values`, 2026-10-30. Design and exactness arguments:
`docs/DATATYPES.md`, sections "Exact data values without a literal cap",
"Object-level projection of data assertions", "Value singletons",
"Counting over data values" and "Open corners".

## What changed

1. **No literal cap.** Above 1,024 value concepts the datatype relations are
   emitted in a linear form (identity star, binary index digits, membership
   profiles) instead of pairwise; `KM_DATA_ASSERTION_LITERAL_CAP` only picks
   between two exact encodings and never declines. Lean:
   `lean/ContextCalculus/LinearValueEncoding.lean`.
2. **Object-level projection** (`frontend/value_projection.rs`): data
   properties used only through functionality, `≤ 1`, domains, atomic ranges
   and sub-properties carry their assertions as domain classes and index
   digits on the subject; no data successor is created.
3. **Value singleton elision** where nothing can force two data successors
   apart (no `≥ n`, `n ≥ 2`, no disjoint data properties, keys or rules).
4. **Negative data-property assertions** are carried as `a : ¬∃u.{v}`.
5. **Counting over finite ranges**: `≥ n p.R` with `|R| < n` is `⊥`, `≤ n p.R`
   with `|R| ≤ n` is `⊤`; covers are enumerated up to the ontology's data
   count bound (IEEE intervals and bounded integer types included); a
   counting restriction next to a range no cover reaches is published as
   not represented. v1.5.4 answered these probes wrongly (see below).
6. **Native bridge admission** reads the linear form and the elided
   singletons with its own gate, accepts exact enumerated covers, and its
   value-pair check is linear.

| state | count |
|---|---|

On the 121 inputs both verify: total wall 735.1 s → 369.4 s, median ratio
0.511, mean ratio 0.698. Largest slowdowns: 8445 +2.3 s (7.5 → 9.8),
443 +1.8 s, 8989 +1.6 s, 668 +1.1 s, 15288 +1.0 s, 11126 +1.0 s; these
inputs now carry thousands of data assertions that v1.5.4 certified away or
dropped, and the extra time is the frontend's carriage (the sort-fixpoint
change cut 15288 from +4.7 s to +1.0 s). Route or accepting mechanism
changed on 3 verified inputs, all faster: 14321, 6934 and 7417 move from
`certified_nominals` to the bridge-first attempt with data assertions as
class. In the rc run, 3561 moved from the bridge to `certified_nominals`
(7.3 → 15.1 s); forced-bridge reruns take 9.9 s and 16.8 s with v1.5.4 and
8.9 s and 8.2 s with the branch, so this is the 8 s bridge-first budget
under load, not a slowdown, and it did not recur in the final run.

Clause streams change for these inputs whenever the conversion runs; the
claim "byte-identical unless the singleton rule applies" holds only for
inputs whose vocabulary stays at or below 1,024 values and whose data
properties are outside the projection gate.
