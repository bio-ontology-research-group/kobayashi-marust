# Baseline measurements for KM v1.7.0 goal 3 (faster and smaller than every baseline)

Written 2026-11-14, read-only survey. Nothing was run on a reasoner; the only computation was
reading existing JSON/TSV records with small Python scripts in
`/mnt/data1/leechuck/km-work/v170/scratch/baselines/` (`ho.py`, `ho2.py`, `ho2.out`, `pool.py`, `jul.py`).
"WT" = `/mnt/data1/leechuck/km-work/wt/v1.7.0`. "W" = `/mnt/data2/workspaces/leechuck/software/kobayashi-marust/.work`.
Anything marked (inferred) is my reading, not a recorded statement.

## 0. Short answer

- The only baseline measured **per input, same day, same protocol, at a recent KM version** is **Konclude**
  (v1.6.4-rc1, 2026-11-14, held-out half, 585 inputs). Against Konclude KM loses on mean wall time
  (3.62 s vs 1.79 s), on median wall time (0.182 s vs 0.159 s) and, in the scoped-watchdog protocol, on median peak
  memory (70.8 MiB vs 48.4 MiB). KM verifies 577 inputs against Konclude's 575.
- HermiT, Openllet, JFact, ELK, Whelk, MORe, RustDL and Sequoia were measured on the full 1,920-input corpus
  (1,708 admitted inputs) under the exact release protocol (1 core, 240 s, 20 GiB), but only at **KM v1.4.5**
  (2026-10-04), and only the pair-wise medians are in the repository. Per-input records are on Ibex only.
  At v1.4.5 KM was 8 to 35 times faster and 4 to 12 times smaller (median) than every Java baseline, and slower than Konclude.
- No record at all: native FaCT++ (only JFact, a Java port, was run), Pellet proper (only Openllet 2.6.5), any query
  workload other than named-class classification, justification and incremental updates, and any comparison on
  the OBO/BioPortal/SNOMED-class corpus at a KM version after v1.3.0.
- Correction to the plan text in `WT/docs/V1.7.0-PLAN.md` section 1: "No current record against HermiT, Pellet/Openllet,
  FaCT++ and ELK" is true for the current KM version, but HermiT, Openllet, JFact and ELK **were** run on the
  1,708-input pool on 2026-10-04 (KM v1.4.5). Details in section 1.2.

## 4. What has never been measured

1. Memory against Konclude: it **is** recorded now (`peak_bytes` in the Konclude and KM chunk files of campaigns A and B). What is missing is a single
   consistent memory protocol: v1.4.5 (unscoped) gave KM 26 MiB vs Konclude 46 MiB; scoped runs from v1.5.3 on give KM about 68 to 72 vs Konclude about 45 to 48 MiB.
   The 2026-10-04 Konclude memory per input is Ibex-only. Konclude `-w 1` memory on the full pool at the current version: not run (only the 585 held-out half).
2. Any baseline other than Konclude at KM >= v1.5.0 on any corpus. HermiT, Openllet, JFact, ELK, Whelk, RustDL, MORe, Sequoia last ran against KM v1.4.5 (2026-10-04).
   Their per-input records are only on Ibex (path in 1.2 B). Not re-run for v1.5.x/v1.6.x.
3. Native FaCT++ and original Pellet (the plan names both). Only JFact 5.0.3 and Openllet 2.6.5 were run.
4. Newer HermiT (1.4.5.519 is the maintained-line jar; 1.4.6 SNAPSHOT in one table). HermiT with several JVM options (e.g. heap beyond 16 GiB) never explored; JVM start-up
   is a floor for every Java baseline (about 4 to 5 s median per input in campaign B).
5. Query workloads: no record for realization / instance types / same individuals (KM `--realize` vs HermiT: only a one-off 19 s vs 7 s remark on wine in
   `WT/docs/REALIZATION.md` line 97), object or data property hierarchies, domains/ranges, `isEntailed` of axioms, `isSatisfiable` per class, and per-query latency in Protege.
   The justification and incremental workloads exist only for KM v1.4.5/v1.5.x (80-ontology panel).
6. Corpora: OBO/BioPortal/FMA/SNOMED-style at KM after v1.3.0; the 2026 ORE-like pool is the only corpus in recent releases. Konclude comparison on the held-out half only
   (the design half was used to tune KM).
7. Multi-core fairness: all release runs are 1 core. Konclude `-w 1` there, but Konclude's default is multi-thread; July panel used `-w 16` for Konclude and 16 cores for KM
   (KM mostly single-thread by routing). No equal multi-core comparison.
8. No Konclude record for mean/median memory on the 2026-10-04 pool in the repository; no memory table anywhere for Openllet, JFact, Whelk, MORe at current KM.
9. Repeated runs: every record is one repetition per input. Release notes show the median ratio drifts between 1.14 and 1.31 across three Ibex runs of the same binaries
   (`WT/docs/RELEASE-1.6.2.md`), so differences of that size are not resolved by one run.

To run all baselines under the current release protocol (one core, 240 s, 20 GiB, scoped watchdog), I see the following gaps (inferred from reading the scripts, not tried):

1. A new runner modelled on `tools/release/v155/ibex/run_konclude.py` for each Java baseline (HermiT, Openllet, JFact, ELK, Whelk): it must use the
   scoped watchdog and pin the JVM (`-Xmx` below 20 GiB headroom; `-XX:ActiveProcessorCount=1`, `-XX:+UseSerialGC` for a one-core fair test). `paper/benchmark/runners/owlapi/` and
   `paper/benchmark/comparative/measure_classification.py` already have the JVM adapters but run under the older unscoped module of 2026-10-04; they need the v1.5.3 protocol modules
   (`tree_watchdog.py`, `scoped_snapshot.py`) from `tools/release/v155`.
2. A real FaCT++ binary (not on Ibex, not in repo) and an original Pellet jar, or a decision to accept JFact and Openllet.
3. Re-use the verified OWL/XML conversions (`.../classification-konclude-53201252/conversion/`) for Konclude and the `canonicalize.py` / `compare_taxonomies.py` protocol modules
   (hashes in every chunk record under `protocol_sha256`).
4. Timing and memory for a verifier-free "baseline solved" rule: the present `verified_solved` for a baseline run is true only if another reasoner independently agrees
   (39 of 49 Konclude "unverified" held-out rows have only self-agreement). Use `konclude_solved()`-style rule for each baseline or you lose 8% of the denominator.
5. Both halves of the pool (1,708) not just the held-out half, plus N >= 3 repetitions or paired same-node ordering to cope with the 1.14 to 1.31 node/day drift.
6. One additional measurement lane for the Protege queries (section 4.5) which has no harness.
7. Compute: Slurm on Ibex only (`gold-6248`, `pi-hohndor`); 1,708 inputs x 6 reasoners x up to 240 s is bounded by about 6 x 18 array tasks of 4 h in the existing sbatch pattern
   (`heldout-konclude.sbatch`: array 0-18 for 585 inputs at chunk 32; pool array 0-59).
