## 2. What has to be certified

For an input O that the route `sroiq-c2a` accepts and that km reports
consistent, km publishes these negative rows:

| Row | Meaning | Count |
|---|---|---|
| consistency | O has a model | 1 |
| sat(A) | A is satisfiable | satisfiable named classes, owl:Thing included |
| nonsub(A, B) | O does not entail A ⊑ B | per satisfiable A, every named B that km does not list above A |
| nontype(a, C) | O does not entail C(a) | per named individual, every named C km does not list |

The proved checker answers one question per call: consistency of an
ontology (`owlC3Consistent`), or a type row (`owlC3TypeRow`, which is
consistency of O plus `ClassAssertion(ObjectComplementOf(C) a)`). The Lean
library also has `owlC3SubRow` (O plus a fresh individual in A and outside
B), but the CLI does not expose it.

### 2.1 One consistency call for many rows: the witness ontology

The prototype certifies many rows with one call. For a chunk of classes it
builds the *witness* W = O plus, for each class A of the chunk, a fresh
individual x_A with

```
ClassAssertion(A x_A)
ClassAssertion(ObjectComplementOf(ObjectUnionOf(B1 ... Bk)) x_A)   -- the non-subsumers of A
```

and, in the first chunk, `ClassAssertion(ObjectComplementOf(ObjectUnionOf(C1 ... Cj)) a)`
for each named individual a with its non-types. Every model of W is a model
of O in which x_A lies in A and outside every B_i, and a lies outside every
C_j. So `"consistent":true` for W certifies consistency, sat(A),
nonsub(A, B_i) and nontype(a, C_j) for all rows W carries. The argument is
monotonicity of models plus a reading of the added assertions; it is not
yet a Lean theorem (request R4 below makes it one, and removes the need
for the extra assertions).

One model serves many rows; where a single model cannot refute all of
A's non-subsumers at once (a disjunction such as `Anytime ≡ {h1, ..., h24}`
in `ore_ont_5107`: x_Anytime must be one of the hours, and each hour is in
some subclass of Anytime), the producer splits the rows over several
individuals x_A, x_A', ... (section 4.4). Named individuals cannot be
copied, so their split rows go to a separate witness.

The negated union keeps the hint small: it adds two names per x_A (a
definer D at x_A and a union name U with B_i ⊑ U and D ⊓ U ⊑ ⊥). A first
version used one fresh class NB per B with `DisjointClasses(B NB)` and
`ClassAssertion(NB x_A)`; the type of x_A then holds every NB, and the
checker's cost per element grows with the type size (section 5).

## 3. Producers compared

### (a) Model construction from the taxonomy

The canonical type of a satisfiable A is its set of entailed named
superclasses, extended to the normal-form names by evaluating their
clauses. This is what the witness asks for: the assertions above force
the named part of x_A's type to be at most km's superclasses. The forced
names propagate bottom-up (definers are defined by clauses), successors are
the canonical types of the fillers plus what universals push, and at-most
clauses merge successors.

Evidence from the prototype: a pure canonical construction (one type per
class, no search) fails as soon as a disjunction or nominal is involved.
On `ore_ont_5107` (SHOIQ, 50 classes, 24 individuals) the joint witness has
no model, 1 of 3,397 negated rows had to move to a second individual, and
the finder had to identify fresh individuals with existing ones (x_Anytime
becomes one of the hours), choose nominal successors for at-least clauses
(`Situation ⊑ ≥1 time_of_day`, range `Anytime`), and backtrack over
disjuncts across nodes (`Dinner_party_at_8pm` must not take an hour that
forces `Out_with_friends`). So (a) alone is not enough; it is the guide
(the target types) of (b).

### (b) An independent small model finder (chosen)

`tools/hints/finder.py`: a completion-graph construction over the
normal form the checker uses, untrusted, with

* types closed by Horn propagation and depth-first choice on disjunctive
  gcis; tree types may not hold a nominal name;
* successors for existential and at-least clauses, universals pushed in
  both directions across every edge (types only grow), at-most clauses met
  by merging successors (into each other, the parent or a core element);
* a core of one element per nominal name; a closure that adds a foreign
  nominal name pulls in that core element's type and identifies the two
  elements (a strict pass first avoids identifying two existing
  individuals); nominal successors pick a core element whose type and
  back-propagated universals fit;
* anywhere pairwise blocking on records `(type, label to parent, parent
  type)`, so the record table of a certificate is the set of records of
  the unblocked tree nodes;
* restarts with nogoods: a failure blames the type of the node being
  processed (and of the node that could not grow); the next run forbids
  those exact types. An unsound nogood costs completeness of the producer
  only.

It runs on the normal form printed by `NFDump.lean`, which calls the same
Lean functions as the checker (`duOff`, `anonOff`, `translateSHOIQD`,
`roleCls`, `encC`/`encS`, `reduceS`), so names and indices match by
construction; the `concepts` count matched `--print-index` on every input
tried.

Handles: TBox and ABox, nominals (C2a core), counting (merging,
nominal successors), inverse roles, transitivity and chains after the Lean
encoding (they are clauses of the normal form), data after the Lean data
reduction (forbidden types are gcis with an empty head; only part 0 of the
data theory, see R6). Not handled: identification of two core elements
forced by an at-most clause on a nominal (rare under C2a), at-most
violations through the parent that need a different parent type, global
backtracking beyond the nogood restarts.

Cost: linear in the size of the completion graph for Horn inputs; the
producer took under 1 s on every sampled witness it finished (section 6).
The cost is elsewhere: the Lean normal-form dump (interpreted, 5 to 40 s)
and the checker (section 5).

### (c) Export from km

What km would have to emit, per satisfiable class A and per individual:
a model fragment over *source* names. From the CB engine: for each context
its set of derived atoms (the positive part of the type at the context
term) and its successor contexts with the role labels; from the tableau
bridge: the completion graph (node labels, edges, blocking). Alignment with
the Lean normal form: km's frontend names fresh symbols differently, so the
export should carry only source class and property names; the producer
then recomputes the definer and encoding names by closing the source types
under the Lean normal form, which is exactly the finder's closure step
(section 3b), with km's successor structure in place of the finder's
search. The gain: no search for disjunctive inputs where km already found
a model (the tableau bridge); the risk: km's CB contexts are not models
(a context's type is a set of consequences, not a choice of disjuncts), so
for non-Horn inputs only the bridge's completion graphs give models, and
those exist only for the inputs routed to the bridge. Cost: an engine
output format and a mapping step, about 3 to 5 days of engine work that
the cargo owner would do (item E16). Recommendation: keep (b) as the
producer, add (c) later as a guide for the inputs where (b) needs restarts
or times out.

## 4. Pipeline

`tools/hints/driver.py ONTOLOGY OUTDIR`:

1. km: `km classify --lines --realize --top` (`KM_THREADS=1`, 300 s).
2. signature: `km-owl-reference --procedure sroiq-c2a --print-index` (class
   and individual IRIs the route knows).
3. rows (section 2); classes in chunks (40 at first, adapted so that the
   flat core stays near 300 elements).
4. per chunk: witness W; `NFDump.lean W` (normal form); finder; hint;
   `hintcheck.py` (a Python mirror of `checkRealisationN` with `CertOK`,
   to catch rejections before the checker falls into its search);
   `km-owl-reference-c3c --procedure sroiq-c2a --hint H W` under
   `ulimit -v 12 GB` and `timeout 300`.
5. no model: localise in normal-form space (drop the gcis `B ⊑ U_x` of
   single rows, greedy by individual, then halves), certify the kept part,
   move the dropped rows to new individuals in the next round (at most 4
   rounds).

A row is counted as certified only when the checker printed
`"consistent":true` for a witness that carries it, in the same run.

### 4.1 Hint forms

*Certificate* hints (core plus `rec`/`ranc`/`rpar`/`rce`/`rkid` records)
are the intended form. Today the checker decides a certificate in time
exponential in the record types (R2), so the producer emits a *flat* hint
whenever possible: every unblocked tree node becomes a core element, an
edge to a blocked node goes to its blocker, and identical siblings get
copies of their target. Folding can break at-most clauses at the blocker,
so the mirror checks the flat hint and the driver falls back to the
certificate when it fails.

## 5. Checker findings and change requests

Measured on the binary `km-owl-reference-c3c` (2026-11-15 08:45) and with
`HintDiag.lean` (interpreted, same library):

* **R1, Closed is decided by enumerating names.** On the witness of one
  class of `ore_ont_10254` (EL, 5,335 normal-form names, 5,396 gcis), a
  two-element flat hint does not check in 300 s. `HintDiag` piece by
  piece: `decide (SRIQ.Closed B t)` for one element takes over 150 s
  (interpreted), while the same condition written as
  `(SRI.Proc.gcis (sriPart B)).all (fun q => !(q.1.all (· ∈ t)) || q.2.any (· ∈ t))`
  takes 20 ms, the lower and upper clause checks 8 ms and 2 ms, the edges
  68 ms. The Prop form `∀ q ∈ gcis, (∀ a ∈ q.1, a ∈ t) → ∃ b ∈ q.2, b ∈ t`
  is slow too, so the bounded quantifiers over `Fin n` are decided through
  an instance that enumerates `Fin n`. Request: in `CheckFast.starOKB`,
  replace `decide (SRIQ.Closed O t)` by a Boolean over the gci list (with a
  lemma `closedB_iff`), and audit the other `decide`s on the hint path
  (`recOK`'s `∀ a ∈ N, a ∉ e.1.1`, `ceOK`, `NomOK`) the same way. This is
  the main reason the prototype certifies only inputs with a few hundred
  names.
* **R2, certificates are decided in exponential time.** `decide (CertOK B
  N h)` uses the instance compiled in `Procedure.lean`, before the `@[csimp]`
  of `CheckFast.lean`, so its star checks still build `Finset.powerset`.
  Reproduction `tools/hints/testdata/cert{4,12,16,20}.ofn` with `.hint`: one
  record of 7, 15, 19, 23 names: 0.08 s, 0.55 s, 11 s (1.8 GB), out of
  memory (9.7 GB). Request: a `CertOKF` with `starOKB` and `@[csimp]`.
* **R3, a rejected hint falls into the search.** `checkRealisationNF`
  calls the elimination (`aliveChk`) and then `searchN`; on real inputs
  both run out of memory or time, so a rejection looks like a timeout and
  the reason is lost. Request: `--hint-only` (no fallback; exit code 5 and
  the first failing core element, record and condition on stderr).
* **R4, a readout row interface.** Request `--rows FILE` (or
  `--classify-hint`): check one hint for O plus `ClassAssertion(A x_A)` for
  every listed class A and print, for each A, every named class outside
  the type of x_A's core element as a certified non-subsumption (and the
  same for named individuals and their non-types). Lean: a lemma that the
  model built from an accepted realisation has core element c in a name iff
  the name is in `ty c` (`checkRealisationN_sound` builds that model), and
  the translation lemma that named class membership at an individual is
  preserved (the type rows already need it). This removes the negated
  assertions (the witness grows by one assertion per class instead of one
  conjunct per row; the number of rows is quadratic in the classes:
  8.16 million on the 2,860 classes of `ore_ont_10254`).
* **R5, a compiled normal-form dump.** `--print-normal-form` printing what
  `NFDump.lean` prints. The interpreted dump costs about 5 s of start-up
  (4 GB of Mathlib), grows with the input (18 s on the 6 MB witness of
  `ore_ont_10254`) and hits the interpreter's recursion limit on large
  ABoxes (`ore_ont_10965`, 108,314 assertions: deep recursion in
  `SRIQKB.assertsOf`; with `ulimit -s unlimited` it ran past 9 minutes).
* **R6, data parts.** `consistentPartsN` tries the hint on part 1, searches
  part 1, then moves to part 2. Request: try the hint on every part first,
  and print which part accepted it.
* **R7, labels.** `RawHint.toHintN` evaluates `lab b c` as a fold over all
  `lab` lines, so the core check costs about k² times the number of lab
  lines (k core elements). Flat hints have k in the hundreds; request an
  array or map built once.

A further observation: the checker accepted every hint that the Python
mirror accepted and that it decided in time; no disagreement between the
mirror and the checker was found.

### 5.1 Targeting the hint-only route `sroiq-hint`

A hint-only route (`--procedure sroiq-hint`, inputs outside C2a, cores
with anonymous shared elements) and a batch mode are being built in
`wt/v170-owl`. The producer fits it as follows:

* the flat hints are already cores with anonymous elements (every
  unblocked tree node is a core element without a nominal name), so they
  need no change beyond the route name;
* `NFDump.lean` must call the new route's translation (one more branch next
  to `chain` and `self`); the finder only reads the clause list, so inputs
  outside C2a need no finder change (C2a is never assumed by the finder);
* the driver's `check` takes the procedure name from `H1_REF` and an
  argument; with a batch mode, one call per input replaces one call per
  chunk, and the readout counts (R4) become certified rows.

## 8. Gaps and plan

Gap by gap, from the prototype to "every negative row of every accepted
pool input certified". Costs are working days of one agent.

| Gap | What blocks | Plan | Cost |
|---|---|---|---|
| G1 checker speed on names | R1: `Closed` (and possibly other `decide`s on the hint path) enumerate `Fin n`; inputs with more than a few hundred normal-form names do not check in 300 s even for a two-element hint | Boolean `closedB` over the gci list with `closedB_iff`, used by `starOKB`; audit `recOK`, `ceOK`, `NomOK`; rerun this sample | 0.5 to 1 (Lean, no new theory) |
| G2 certificates | R2: `CertOK` decided with the exponential star | `CertOKF` with `starOKB` and `@[csimp]`; then the producer can emit certificates (no folding, no copies, smaller hints) | 0.5 |
| G3 quadratic row count | 8.16 million rows on a 2,860-class input; the witness carries every row | R4 readout interface plus its Lean lemmas; the witness then holds one assertion per class, and the producer's readout already counts the rows it would certify (column `readout_rows`) | 2 to 4 (Lean) + 0.5 (producer) |
| G4 data | the route enumerates every part of the data theory (`partsOf`: compositions of each small cell over 2^s groups, s the number of data names) before trying the hint; on `ore_ont_7839` (FOAF, 14 data properties) the enumeration does not finish in 100 s and the checker runs out of memory | R6: the hint names its part (the counts), the checker checks that part only, and enumerates lazily otherwise | 1 to 2 (Lean) + 0.5 (producer: pick the part from the model's data values) |
| G5 normal-form dump | R5: interpreted Lean, 5 to 40 s per witness, deep recursion on large ABoxes | `--print-normal-form` in the checker binary | 0.5 |
| G6 rejected hints are silent | R3: a rejection falls into the search | `--hint-only` with the failing condition | 0.5 |
| G7 producer completeness | no model found: at-most violations through the parent, identification of core elements forced by at-most clauses on nominals, deep disjunctive interactions beyond nogood restarts | a proper backtracking tableau in Rust (`tools/hints/`, no `engine/` change), or km export (3c) as a guide | 3 to 5 |
| G8 large inputs | inputs over 10 MB: km itself, the dump and the producer in Python | Rust producer (G7), compiled dump (G5); certification time then dominated by the checker, linear in the hint after G1 to G3 | with G5, G7 |
| G9 batch | one witness per chunk of classes, one parse and translation per call | R4 also serves as the batch interface: one call per input | with G3 |

Order: G1 and G2 first (a day, and they decide whether flat hints are
needed at all), then G6 and G5 (tooling), then G3 (the Lean lemma), G4,
and G7 in parallel with G3. After G1 to G3 the prototype's own numbers
predict the reach: every input whose hint the mirror accepts would be
certified (the column `mirror_only_rows` counts the rows whose hints the
mirror accepted but the checker did not decide in time).
