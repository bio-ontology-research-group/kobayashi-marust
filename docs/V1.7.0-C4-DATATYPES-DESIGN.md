# Stage C4: data properties and datatypes (design)

Supervisor's design note, 2026-11-14. 450 pool inputs use datatypes; all
51 SHIQ-with-datatypes inputs of the C1 probe declined on them. Facets
occur in 17 inputs (numeric bounds only). Most frequent datatypes:
string, int, boolean, float, integer, double, dateTime, anyURI,
nonNegativeInteger, positiveInteger, rdfs:Literal, decimal.

## 1. Idea

A data value has no successors and no inverse: data properties only
point from individuals to values. So data reasoning is local to one
element: its data neighbours are leaves of its star. The only global
fact needed is how many distinct values a combination of data ranges
has. That is the *datatype oracle*; everything else reuses stars.

## 2. Normal form `SRIQD`

New namespace `ContextCalculus.SRIQD` (new files; `SRIQ` untouched, with
an embedding lemma as `SRIQ.ofSRI`). Parameters: concept names, role
names, data property names `DProp`, and *data atoms* `DAtom` (one per
atomic data range occurring in the ontology: a datatype, a facet
restriction, a `oneOf`). Clauses of `SRIQ` plus

```
| dEx (a : CName) (u : DProp) (pos neg : List DAtom)        -- a ⊑ ∃u.(⋀pos ⊓ ⋀¬neg)
| dAll (a : CName) (u : DProp) (head : List (DAtom × Bool)) -- a ⊑ ∀u.(⋁ literals)
| dAtLeast (a) (n : Nat) (u) (pos neg : List DAtom)
| dAtMost (a) (n : Nat) (u) (pos neg : List DAtom)
| dSub (u v : DProp)                                        -- u ⊑ v
```

(Data ranges are in a clausal form over atoms; the translation produces
it. Functional data property: `⊤ ⊑ ≤1 u.⊤`.) An interpretation adds a
value type `V`, `d : DProp → D → V → Prop` and `atom : DAtom → V → Prop`.
The semantics is relative to a *data theory* `Θ`: a class of admissible
pairs `(V, atom)` (for OWL: the datatype map fixes both). Entailment
quantifies over admissible data interpretations.

## 3. The oracle

A *value type* is a set `τ` of atoms (the atoms a value satisfies). The
oracle of a data theory is `card : Finset DAtom → Option Nat`:
`card τ = some k` if exactly `k` values have value type exactly `τ`
in every admissible interpretation (0: `τ` is not realisable), `none` if
there are infinitely many. Requirement on the theory (`OracleSpec`): for
every admissible interpretation the number of values of each value type
is as `card` says. (The OWL 2 map has one interpretation up to the free
datatypes, so this is a property of the map.)

## 4. Stars with data leaves

A data neighbour is `(Lu, τ)`: an up-closed set of data properties
(under `dSub`) and a value type. A star is `(t, N, Dn)` with `Dn` a list
of data neighbours. `DStarOK`:

- the `SRIQ` conditions for `t` and `N`;
- every `τ` in `Dn` is realisable, and for each `τ` the number of
  entries with value type `τ` whose values must be distinct is at most
  `card τ` (entries are distinct values; two entries with the same `τ`
  need two values);
- `dAll a u head` with `a ∈ t`: every entry with `u ∈ Lu` satisfies some
  literal of `head` (read on `τ`);
- `dEx`, `dAtLeast`, `dAtMost` with `a ∈ t`: counts over the entries with
  `u ∈ Lu` whose `τ` contains `pos` and avoids `neg`.

Records, `Good`, self-supporting sets as in `SRIQ` (data leaves need no
support). Characterisation `entailsSub_iff_dstar` by the same two
directions: from a model, the data neighbours of `x` are the witnesses
chosen for its data clauses with their labels and value types (distinct
values give distinct entries; values of one type are at most `card`
many); to a model, pick for each node and each value type as many
distinct values as its entries need (possible by `OracleSpec`), sharing
values between nodes freely.

The bound for the executable search adds the data at-least numbers.

## 5. ABox

`dAssert a u τ`-style assertions (`DataPropertyAssertion(u a "l"^^dt)`):
the literal becomes an atom `{l}` with `card = 1` (or 0 if ill-typed
against other atoms), and the block of `a` gets a data neighbour that
must contain it. Negative data assertions forbid it. Extend
realisations (`SRIQ/ABox.lean`) accordingly.

## 6. The OWL 2 datatype map (second half of the stage)

Instantiate the data theory for the map: value spaces and lexical
mappings for the numeric tower (`owl:real`, `owl:rational`,
`xsd:decimal`, `xsd:integer` and its derived types), `xsd:string` and
derived, `xsd:boolean`, `xsd:float`, `xsd:double`, `xsd:dateTime`
(`Stamp`), `xsd:anyURI`, binary types, `rdf:PlainLiteral`,
`rdf:XMLLiteral`, `rdfs:Literal`; facets. The oracle for a value type:
intersect per primitive type (the primitives are pairwise disjoint), on
numerics intersect intervals and count integers in bounded integer
intervals, floats are finite sets, strings with length and pattern
facets (pattern: decline at first, 0 corpus inputs). Then `OWL.EntailsSub`
is taken at the OWL 2 map (a definitional change in the capstones:
today it quantifies over every map).

## 7. Order

1. `SRIQD/NormalForm.lean`, data theories, oracle spec, embedding.
2. `SRIQD/Stars.lean`: `entailsSub_iff_dstar`.
3. `SRIQD/Procedure.lean`: elimination with the oracle, `classifyQD_spec`;
   transitivity carries over (data clauses pass through `encTransQ`).
4. ABox with data assertions.
5. A small concrete theory for tests: integers with bounds, booleans,
   strings without facets; tests: functional data property with two
   different literals (inconsistent), `≥3 u.boolean` (unsatisfiable),
   `∃u.int[≥5] ⊓ ∀u.int[≤3]` (unsatisfiable), `≥2 u.int[≥1, ≤2]`
   (satisfiable), `≥3` of the same (unsatisfiable).
6. The OWL 2 map and its oracle; translation from OWL; capstones.
