# HermiT parity scoreboard for the KM Protégé plugin, after the W10 conventions work

Ontologies: 36. Method-ontology cells where HermiT answered or failed: 1506 (24 further cells left out because HermiT timed out or never reached them). Reasoner calls compared: 97447.

**Parity score (strict): 59.8%** (900 of 1506 cells). Lenient score, where a node grouping difference with the same entities does not count: 59.8% (900 of 1506). Adjusted score, which also ignores differences that consist only of owl:Thing or owl:Nothing (or the top and bottom properties) appearing in one answer and not the other: 60.2% (907 of 1506).

Splitting each method by the kind of argument (named entity, anonymous class expression, top or bottom entity, inverse property expression) gives 2503 cells and a strict score of **71.5%** (1789 cells), adjusted 71.8% (1796 cells).

A cell is one OWLReasoner method on one ontology; it counts for KM when KM agrees with HermiT on every call of that method (HermiT errors that KM answers are not held against KM), or when HermiT fails on the whole cell and KM answers. Settings: HermiT 1.4.3.456 with `ignoreUnsupportedDatatypes = true`, KM plugin through the OWL API 4.5.29, `KM_THREADS=1`.

## Run settings and ontologies

- Date 2026-11-14. Harness `protege-parity/` and plugin on branch `v170/plugin-conventions` (development/v1.7.0 plus the W10 plugin changes). Plugin 1.6.4 build, OWL API 4.5.29, HermiT 1.4.3.456 (Protégé's configuration, `ignoreUnsupportedDatatypes = true`), km `scratch/w2p/km` (the same binary as the baseline), `KM_THREADS=1`, one ontology at a time, Java 21.
- Ontologies: the 36 of the baseline's 42 that KM classifies (the baseline's 40 corpus ontologies plus wine and food, without ore_ont_2526, 7532, 8250, 9662, 8273 and 13700, which KM refuses or does not finish). The baseline numbers quoted below are recomputed on the same 36 files from the baseline JSON.
- Time limits: 180 s of wall time per reasoner per ontology and 20 s for a single query after precompute. ore_ont_5841 needs about 175 s of KM time, so it was run again with 600 s (the 180 s run is kept in `out-180/`), as in the baseline. HermiT hit its limit on 7 ontologies at 180 s (food, wine, ore_ont_13153, 13545, 14396, 15108, 1834), always in the late phases; both reasoners finished ore_ont_5841 at 600 s; cells with no HermiT answer are left out of the score.
- Sampling and settings as in the baseline (seed 1, up to 200 entities per kind, 16 generated anonymous class expressions, up to 5 axioms per axiom type).
- Harness changes for this run: `getTimeOut` is informational (HermiT gets its own `Configuration` in the harness and reports -1; given an `OWLReasonerConfiguration` it returns the configured value, as KM does), and `km_unsupported` also covers `isEntailmentCheckingSupported` or `isPrecomputed` false where HermiT says true and a `getPrecomputableInferenceTypes` that is a strict subset of HermiT's. The `isPrecomputed` rule was added after the run and applied to the stored files with `parity_reverdict.py`. After a review the data property fragment was tightened (a functional data property next to a nominal or a rule is refused); the 15 ontologies with data property answers were run again and no answer changed from answered to refused.

## Reading the result

- **No cell is wrong any more.** Of the 1506 cells, 900 agree, 486 are KM unsupported (KM throws instead of answering) and 120 differ. Every one of the 120 is adjudicated below: HermiT wrong (the bottom object and data property domains and ranges, the disjoint data properties of `owl:bottomDataProperty`, a direct-types quirk on wine, which HermiT showed in the first run only) or a convention on which the reasoners differ and KM's answer is the accurate one (`isPrecomputed` true for `CLASS_ASSERTIONS` and `SAME_INDIVIDUAL`, which KM holds and HermiT reports false for). On the same 36 ontologies the baseline had 931 agreeing cells, 70 unsupported and 538 differing; most of those 538 were empty answers where HermiT had facts.
- The strict score does not rise (59.8% against 60.5% on these 36 files) because the baseline counted an empty answer as agreement whenever HermiT's answer was empty too, for example `getObjectPropertyValues` on an individual without values. KM now throws there, which is the unsupported column, not the agreement column. Counted by what KM did wrong or left out: the baseline had 538 differing cells and 70 unsupported ones; this run has no cell where KM is wrong and 486 where it declines to answer.
- Calls: `differ_content` fell from 15,454 to 232; `km_unsupported` rose from 2,108 to 24,038 because every anonymous class expression, property value, disjointness and different-individuals call now throws. The 24,027 are the engine work items (listed in `protege/README.md`, "Queries that throw").
- Inside the data property fragment (24 of the 36 ontologies: 9 with no data property and 15 of the 27 that have some) the data property hierarchy, equivalents, domains and top and bottom nodes agree with HermiT on all sampled calls, apart from the two HermiT-wrong shapes H5 and H6. The other 11 ontologies with data properties are outside the fragment (a data property in a class axiom, disjointness, complex range, or domains that cannot be combined) and throw; ore_ont_5014 is inconsistent and both reasoners throw.
- A KM classification that fails is now remembered for that version of the ontology (unit tests `ConventionsTest`); the harness does not exercise this, because it loads each ontology once.

Call verdicts, all calls: agree 69808, both_error_different 40, both_error_same 2589, differ_content 232, hermit_error 7, hermit_timeout 733, km_unsupported 24038.

## What the harness does not cover

- Ontology edits. Every run loads the ontology once and queries it. `flush`, buffering, pending changes after an edit, incremental updates and the reasoner state after a failed run are not exercised (`getPending*` and `flush` are asked on an idle reasoner).
- Interruption and limits. `interrupt()` is only called idle or after a query ran past the per-call cap; progress monitor calls, `TimeOutException` from a configured timeout and Protégé's Stop button are not tested. The worker kill is the only hard limit.
- Configuration variants. One HermiT configuration (Protégé's, `ignoreUnsupportedDatatypes = true`), the default fresh entity policy and the default individual node set policy. `BY_SAME_AS`, `THROW_EXCEPTION` and the timeout are not varied.
- Protégé itself. No Protégé window, preference mapping, explanation workbench or DL Query tab. The harness checks the `OWLReasoner` answers those features read, not the features.
- Query shapes outside the plan: queries on anonymous individuals, data range class expressions with facets in `getInstances`, SWRL rules, keys, imports other than the W3C wine and food pair, and axioms the generator has no template for (keys, datatype definitions, annotation axioms beyond those in the ontology).
- Sampling. At most 200 entities per kind, 6 for the disjoint and different-individual queries, 30 property expressions for domains and ranges, 40 individuals by 15 properties for values, 5 axioms per axiom type. One seed (1). A difference outside the sample is not seen; the counts in the difference tables are counts of sampled calls, not of ontology facts.
- Correctness of HermiT. The harness is differential. Where both agree it does not know they are right; where they differ the adjudication section decides by hand on a sample, and not every shape has a source check.
- Scale and speed. Ontologies under 2 MB, one run per reasoner, one machine, `KM_THREADS=1`, a time limit that ended several runs, no repeats. Phase times are indicative only.
- The Protégé 6 build (OWL API 5) is not run; the module builds against OWL API 4.5.29 and HermiT 1.4.3.456.
