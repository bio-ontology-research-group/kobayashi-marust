# Protégé parity of KM v1.7.0 against HermiT, final run (parity2)

Branch `v170/w14-parity` (development `1106b555`, merged with development `ba95c23c` before this document). KM binary `/mnt/data1/leechuck/km-work/v170/scratch/bin/km-ec070684-sup` (built at `1106b555`; the later merges touch `engine/` only in a test file and a small diff that I did not re-measure). HermiT 1.4.3.456 with `ignoreUnsupportedDatatypes = true`, OWL API 4.5.29. KM runs through the plugin class `KMReasoner` with `--lenient --unknown-datatypes=free`, `KM_THREADS=1`. Raw results, scripts and reproduction files are in `/mnt/data1/leechuck/km-work/v170/scratch/parity2/` (`out/`, `adj/`, `calls.tsv`, `final.py`, `repro/`).

## 1. Outcome

- Out of 545,108 compared calls that both reasoners answered or both refused identically, KM matches HermiT in all but 2,106 calls where the answers differ. I decided every one of those 2,106 by the OWL 2 direct semantics: KM is right in 2,102, HermiT is right in 4, none is undecided, none has both wrong.
- The 4 calls where HermiT is right come from 2 causes. (a) KM misses a role assertion that follows from a role chain through an anonymous individual (`getObjectPropertyValues`, repro `h_f9002_44_chain_anon.ofn`). (b) After an interrupted property classification KM returns an empty set from `getObjectPropertyValues` where a fresh KM session returns the correct answer (ontology `ore_ont_9662`, repro `Mini2_interrupt_then_values.java`).
- KM does not answer 3,511 calls that HermiT answers (timeouts or exhausted budget) and refuses or fails 46 more. In another 8,045 calls KM was killed with exit 143 after an earlier interrupt (section 6); most of those are one effect in 4 ontologies.
- The strict-mode part is incomplete: only the first 51 of the 212 inputs ran (section 2). HermiT answers anything on only 4 of those 51.

## 2. What I ran, and what I changed

Ran:
- 200 random small ontologies with individuals (`fuzz200`, seeds 9001 and 9002, generator `genfuzz.py`, 100 each): all 200.
- The 98-ontology sample of the W13 report (`sample98`: the 42 of `ontologies.txt`, the 40 of `ontologies-round2.txt` and the 16 held-out ones): all 98.
- The 212 inputs that strict mode rejected (`invalid212`): 51 of 212, the first 51 in list order. The rest were not run. A HermiT run on these takes its full 300 s on almost every input, so the 212 would need about 10 hours on two slots. I stopped at 51 on purpose and did not sample at random.
- Every query family the earlier reports cover: class hierarchy, equivalents, (un)satisfiability, object and data property hierarchy, types, instances, same and different individuals, object and data property values, consistency, entailment, disjoint classes, precompute and meta calls; the inconsistent ontologies are in section 9. The query plan is the one of `protege-parity` (`Plan.java`, seed 1, at most 200 entities per kind), unchanged.
- HermiT 300 s per input with `-Xmx8g`; KM under 300 s per input; 20 s cap per query after precompute. Two JVMs at a time at most, never cores 40 or 44.
- One deviation: for an `invalid212` input on which HermiT answered 20 calls or fewer, KM ran with a 60 s budget instead of 300 s, because no comparison is possible. 47 of the 51 inputs are of that kind.

JVM crashes on this host, and how I handled them. The host has `vm.overcommit_memory=2`. The 14 `hs_err_pid*.log` files of the earlier agent all say "Out of Memory Error (os_linux.cpp:2829) ... committing reserved memory". The system-wide commit charge (`Committed_AS`) sat at 273 to 277 GB against a `CommitLimit` of 276.9 GB because of other jobs, so every new commit failed. The biggest failing request, 2.11 GB, was the default initial heap (1/64 of the 125 GB RAM) of a worker; the rest were 64 KB commits during JIT or heap growth. The inputs did not cause it. I started every JVM with `-Xms32m -XX:+UseSerialGC -XX:ReservedCodeCacheSize=64m -XX:MaxMetaspaceSize=256m` and the explicit `-Xmx8g` cap, and the driver reran any input whose worker ended `crashed` or whose KM answered with an allocation error ("Resource temporarily unavailable", "memory allocation", exit 134), up to 3 times. After the reruns no input ended `crashed`, and none of these is counted as a difference. 18 inputs were rerun (the earlier results are in `old/`): `f9001_6`, `f9001_76`, `f9002_12`, `f9002_43`, `ore_ont_10127`, `10173`, `10320`, `10409`, `10776`, `12653`, `13545`, `14684`, `15667`, `15682`, `16723`, `1707`, `3726`, `8975`; `f9001_79` had no result and ran for the first time. Four of the later KM errors were not environmental and persisted on rerun (sections 5 and 7).

How differences were decided. HermiT's own `isEntailed` is the oracle (`Probe.java`, driven by `adjudicate2.py`, 600 s budget per ontology); for each element in the symmetric difference of the two answers it asks the entailment that the method contract names, and for direct queries it also asks minimality. Three rules shortcut it:
- Domain and range of `owl:bottomObjectProperty` and `owl:bottomDataProperty` (`getObjectPropertyDomains`, `getObjectPropertyRanges`, `getDataPropertyDomains`): the property has an empty extension, so every class is a domain and range; the minimal one is `owl:Nothing`. KM returns that; HermiT returns `owl:Thing`. 426 calls were decided by this rule alone (answer fits it exactly); the oracle decided the other 1,252 of these 1,678 calls and agreed with the rule every time.
- `getDisjointDataProperties(owl:bottomDataProperty)`: the bottom property is disjoint with every data property including itself; HermiT omits itself.
- Individual cases decided by hand are in section 4.

## 4. Where HermiT is right, and the hand-decided cases

HermiT right (4 calls, 2 causes). Both reproduce; I ran them.

1. `getObjectPropertyValues(a4, c1)` and `(a4, inv c1)` on `fuzz200/f9002_44.ofn`. Reproduction: `repro/h_f9002_44_chain_anon.ofn` (10 lines). Axioms: `B(a4)`, `B SubClassOf ObjectSomeValuesFrom(inverse s3, B)`, `inverse s3 SubPropertyOf s1`, `s1` symmetric, `s1 o s3 SubPropertyOf c1`. There is an anonymous x with `s3(x, a4)`; so `s1(a4, x)` and `s1(x, a4)`; the chain gives `c1(a4, a4)`. HermiT returns {a4}; KM returns {}. KM also answers `false` to `isEntailed(ObjectPropertyAssertion(c1 a4 a4))` on the same file, a wrong "not entailed" answer. This is a missing inference (completeness), not an unsound one.
2. `getObjectPropertyValues(CHEMINF_000198, SIO_000028)` and `(..., SIO_000001)` on `ore_ont_9662`. `ReflexiveObjectProperty(SIO_000028)` gives `SIO_000028(a, a)` for each individual `a`, and `SIO_000028 SubPropertyOf SIO_000145 SubPropertyOf SIO_000322 SubPropertyOf SIO_000001` gives the second. A fresh KM session answers {a}; I ran that (`shrink/Mini`). In the parity run the KM call came after a `getTopObjectPropertyNode` that hit the 20 s cap and was interrupted, and then returned {}; I reproduced that order (`repro/Mini2_interrupt_then_values.java`, run with `repro/mini2.sh <ontology> <individual IRI> <property IRI>`: it prints `RESULT values 0`). A short ontology does not show it, because the interrupt has to hit a running classification, so there is no small file. I read this as: after `interrupt()` of a running property classification KM keeps wrong state and answers later value queries silently with an empty set (inferred from the two runs, not traced in the code).

No case is undecided.

## 6. Interrupted calls and the exit 143 calls

The 8,045 "KM killed (exit 143)" calls (6,651 object property hierarchy, 1,235 equivalents, 72 types and more) come from 4 corpus ontologies (`12723`, `7532`, `9662`, `wine`) and 1 fuzz input (`f9001_79`). In each, the first `getTopObjectPropertyNode` or realization call passed the 20 s cap, the harness interrupted it, and every later call of the same kind failed at once with `property classification failed (exit 143)`, `ReasonerInterruptedException`. That means after one `interrupt()` KM keeps refusing the same kind of query (observed, 4 ontologies). I did not look in the code for the flag. `wine` needs 12.6 s for `getTopObjectPropertyNode` alone (measured with `Mini5` on a loaded host); W10 reported KM finishing `wine` in 7 s in total, so this is slower than before (host load may explain part of it; I did not compare on an idle host).

## 7. Queries the plugin answers with "unsupported" (KM declines, HermiT answers)

46 calls plus 8,045 killed calls (section 6):
- 40 calls: a class expression query with `ObjectMinCardinality` over a non-simple role is rejected as `invalid OWL 2 DL input: ObjectMinCardinality requires ...` (getInstances 10, getSubClasses 10, getSuperClasses 10, isSatisfiable 5, getEquivalentClasses 5). Inputs: `ore_ont_10776`, `13153`, `13413`, `1834`, `6615`, and the repro `h_f9002_44_chain_anon.ofn`. HermiT answers them. This is correct under the OWL 2 DL restriction on query expressions; HermiT is more lenient.
- 4 calls on `ore_ont_8250`: `getDisjointDataProperties` fails with `unsupported: DL-safe rules reach class queries`.
- 2 calls: `isPrecomputed` and `getPrecomputableInferenceTypes` report fewer capabilities than HermiT.

HermiT errors where KM answers (no comparison, I did not check KM's answer): 14,240 calls. Causes: 11,062 calls on 7 ontologies with SWRL built-in atoms (`A SWRL rule uses a built-in atom, but built-in atoms are not supported yet`; `sample98`: `15993`, `714`, `3726`, `10860`, `7278`, `15753`, and one `invalid212` input; 10,420 calls in `sample98`, 642 in `invalid212`); 3,000 calls on `ore_ont_3545` (`MalformedLiteralException` for an `xsd:anyURI` literal); 102 calls with `owl:topDataProperty` use; 75 `NullPointerException` in HermiT's `HierarchyNode.isEquivalent...` on `isEntailed` (46 in `fuzz200`, 29 in `sample98`). KM answers these in the lenient mode that the plugin uses.

## 8. HermiT timeouts

300,971 calls have no HermiT answer because HermiT timed out or stopped. HermiT answered more than 20 calls on 89 of the 98 `sample98` ontologies and on 4 of the 51 `invalid212` inputs; on `invalid212` its precompute phase timed out on 32 inputs, 13 more did not return after the interrupt, 1 worker was killed after 360 s, and 1 failed at creation (SWRL built-in). The reasoners cannot be compared there.

## 9. Inconsistent ontologies

8 inputs are inconsistent for HermiT (`f9001_41`, `f9001_69`, `ore_ont_13405`, `5014`, `8362`, `8941`, `10906`, `13880`). On all 8, `isConsistent` returns false in both reasoners, and every other query that HermiT refuses with `InconsistentOntologyException` is refused by KM with the same exception class (counted equal): 1,351 + 1,349 + 4,081 + 2,589 + 2,860 + 4,390 + 2,960 + 2,953 calls, plus 59 agreeing meta calls each. No difference. The new proved refutation checker (development `ba95c23c`) was not part of this measurement.
