## 1. Facts that shape the whole job

1. KM classifies in the constructor (`KR` constructor calls `classify()`), and `precomputeInferences` is a no-op (`KR.precomputeInferences`). HermiT loads and clausifies in the constructor (`R.loadOntology`) and classifies lazily or in `precomputeInferences`.
2. Protégé stores the new reasoner in `runningReasoner` only after `ReasonerUtilities.createReasoner` returns (`OWLReasonerManagerImpl.ClassificationRunner.ensureRunningReasonerInitialized`). `killCurrentClassification` calls `runningReasoner.interrupt()` and does nothing when it is still null. So the Stop button cannot reach KM's first classification, because KM does all its work inside the constructor. A re-run on an existing reasoner goes through `flush()` and can be interrupted.
3. Protégé catches only `ReasonerInterruptedException` and `InconsistentOntologyException` around the run (`ClassificationRunner.run`). KM's `interrupt()` kills the native process and closes the session (`Classifier.Session.interrupt`); the blocked `classify` then fails with a plain `RuntimeException` wrapped in `ReasonerInternalException` (`KR.classifySource`, `Classifier.Session.exchange`). HermiT throws `ReasonerInterruptedException` / `TimeOutException` from `InterruptFlag.checkInterrupt`.
4. Protégé's own class views send anonymous class expressions to the reasoner, even with DL Query closed (section 4). KM returns empty answers or `true` for them.
5. The only `OWLReasonerConfiguration` input KM reads is none: `KMReasonerFactory` ignores `config` (progress monitor, timeout, fresh entity policy, individual node set policy are never read; grep over `protege/src/main/java` finds no use). `KMReasonerInfo` does not override `getConfiguration`, so Protégé gets `SimpleConfiguration(monitor)` from `AbstractProtegeOWLReasonerInfo.getConfiguration` (Protégé source), and the monitor is never called.

## 5. `isEntailed`

KM: `isEntailmentCheckingSupported` is true only for SUBCLASS_OF (`KR`). `isEntailed` throws `UnsupportedEntailmentTypeException` for any other axiom type and for SubClassOf with an anonymous side. `isEntailed(Set)` throws for the first non-SubClassOf axiom, even an annotation or declaration (HermiT skips those). Inconsistent ontology returns true for supported SubClassOf shapes. Gap: every row above; the plan's Section 2 table already lists the reductions to fresh classes, and the table above is the HermiT list to check completeness against.

## 6. Datatypes and facets

### 6.1 HermiT (`datatypes/DatatypeRegistry` and handlers, `dd2a021a`)

`DatatypeRegistry` registers exactly these handlers: `OWLRealDatatypeHandler`, `DoubleDatatypeHandler`, `FloatDatatypeHandler`, `BooleanDatatypeHandler`, `RDFPlainLiteralDatatypeHandler`, `DateTimeDatatypeHandler`, `BinaryDataDatatypeHandler`, `AnyURIDatatypeHandler`, `XMLLiteralDatatypeHandler` and an internal anonymous-constants handler. Its error text says it "supports all and only the datatypes of the OWL 2 datatype map".

| Handler | Datatypes | Facets accepted (`validateDatatypeRestriction`) |
|---|---|---|
| OWLReal | owl:real, owl:rational, xsd:decimal, integer, nonNegativeInteger, positiveInteger, nonPositiveInteger, negativeInteger, long, int, short, byte, unsignedLong, unsignedInt, unsignedShort, unsignedByte (note: literals of owl:real are always malformed, `parseLiteral`) | minInclusive, minExclusive, maxInclusive, maxExclusive |
| Double, Float | xsd:double, xsd:float | the same four |
| DateTime | xsd:dateTime, xsd:dateTimeStamp | the same four, with dateTime values |
| Boolean | xsd:boolean | none |
| XMLLiteral | rdf:XMLLiteral | none |
| RDFPlainLiteral | rdf:PlainLiteral, rdf:langString, xsd:string, normalizedString, token, Name, NCName, NMTOKEN, language | xsd:minLength, maxLength, length, pattern, rdf:langRange (per type; the code at `RDFPlainLiteralDatatypeHandler` lines ~110-140 and ~273-340 decides which apply to which type; I did not tabulate this per type) |
| BinaryData | xsd:hexBinary, xsd:base64Binary | length, minLength, maxLength |
| AnyURI | xsd:anyURI | length, minLength, maxLength, pattern |
| built in elsewhere | rdfs:Literal (`InternalDatatype.RDFS_LITERAL`); facets on it throw `IllegalArgumentException` | n/a |

OWL 2 datatype map: all of the above appear in the map. Nothing in the map is missing from HermiT's registry (checked by name against the list in the OWL 2 Syntax, section 4, from memory; the spec text was not fetched, so treat as unverified at the level of single names).

Rejection behaviour:
- A datatype outside the map throws `UnsupportedDatatypeException` (`DatatypeRegistry.getDatatypeHandlerFor`), unless `Cfg.ignoreUnsupportedDatatypes` is true. Then the datatype is added to `m_allUnknownDatatypeRestrictions` and treated as a free, uninterpreted datatype with a warning (`OWLClausification.DataRangeConverter.visit(OWLDatatype)`, `visit(OWLLiteral)`).
- In Protégé the flag is true: `PRF.getConfiguration` sets `ignoreUnsupportedDatatypes = true`, and `RF.getProtegeConfiguration` keeps a `Configuration` instance as given. So in Protégé HermiT does not reject `xsd:date`, `xsd:time`, `xsd:duration`, `xsd:gYear` or custom datatypes without definitions; it treats them as free datatypes. `docs/DATATYPES.md` ("Open corners") says "HermiT rejects such inputs"; that is true of the plain API default, not of the Protégé path.
- An unsupported facet on a supported datatype throws `UnsupportedFacetException` and is not covered by the ignore flag (`visit(OWLDatatypeRestriction)` has no catch).
- Malformed literals throw `MalformedLiteralException` from the handler.

### 6.2 KM (`docs/DATATYPES.md`, `engine/src/frontend/datatypes.rs`)

- Named types (`named_dt_kind`): integer tower, decimal, owl:real, owl:rational, float, double, boolean, the string family down to NMTOKEN, rdf:PlainLiteral, rdf:XMLLiteral, anyURI, hexBinary, base64Binary, dateTime, dateTimeStamp. Types outside the map (`date`, `time`, `g*`, `duration`) and custom datatypes: free abstraction (docs "Open corners").
- Facets: only the four `min/max Inclusive/Exclusive` (`builtin_facet_key`). Decided exactly for numeric, IEEE and dateTime ranges.
- Length, minLength, maxLength, pattern: "DROPPED on the automatic route, refused on the forced nominal routes" (docs "Open corners", rows `length_*`, `pattern_*`). `langRange`: not mentioned in the docs or in the facet table I read; unverified, assume the same.
- The plugin refuses any classification where the native side reports dropped clauses: `Classifier.Session.transact` (line ~238) throws "Kobayashi-MaRust declined a complete classification" and `KR.classifySource` wraps it in `ReasonerInternalException`. So in Protégé, an ontology with a pattern or length facet fails to load into KM where HermiT classifies it.
- `rdf:XMLLiteral`: exact for text and attribute-free elements; attributes, prefixes, comments, processing instructions DROPPED (docs).
- n-ary `DataSomeValuesFrom`, `HasKey` over data properties: refused (docs). HermiT's `HasKey` entailment handles data properties.
- docs note one fixture where HermiT and KM differ on the string chain (`string_chain`); not adjudicated here.

## 7. SWRL / DL-safe rules

### HermiT (`structural/OWLNormalization.RuleNormalizer`, `OWLClausification.NormalizedRuleClausifier`)
- Supported atoms: ClassAtom (also complex class expressions, normalised to new named classes), ObjectPropertyAtom, DataPropertyAtom, DataRangeAtom (complex ranges normalised), SameIndividualAtom, DifferentIndividualsAtom; arguments: variables, named individuals, literals. Rules with several head atoms are split (Lloyd-Topor). Rules with an empty body are turned into facts.
- Rejected with `IllegalArgumentException`: SWRL built-in atoms (`OWLNormalization` lines ~1138, 1360; the clausifier throws `UnsupportedOperationException` "built-in atoms are not yet supported"); anonymous individuals in rule atoms; head variables that do not occur in the body; data range variables in the head but not the body; rules that mix description-graph and ordinary properties.
- A `SWRLRule` cannot be an additional axiom in a query (`isUnsupportedExtensionAxiom`) and `isEntailed(SWRLRule)` throws.
- Readme: "supports DL-safe SWRL rules". Whether HermiT checks DL-safety, or applies rules to anonymous tableau nodes too, I did not verify.

### KM (`docs/DL-SAFE-RULES.md`; I read the header, the pipeline table, the tier list and the soundness note, not every section)
- FIRED: ClassAtom over named classes, ObjectPropertyAtom, SameIndividualAtom (named individuals or variables).
- DEFERRED: rules with a DifferentIndividualsAtom; dropped from the rule clauses and counted in `dropped`.
- DECLINED (whole rule-aware route refused): DataPropertyAtom, BuiltInAtom, DataRangeAtom, ClassAtom over a complex expression (docs "The three tiers"). The v1.4.4 section says an accepted classification must account for the full rule obligation; invalid input exits with code 2, incomplete support with code 3.
- Plugin: a rule with a built-in atom makes the update fail atomically with `ReasonerInternalException` and the previous answers stay (`ReasonerTest`, rollback test around line 400). The same exception type is what HermiT's `IllegalArgumentException` becomes from the user's view, so built-ins are at parity (both reject).
- The doc's tier section is marked historical in places; whether DEFERRED and DECLINED are still the live behaviour at 5b9df848 is unverified (later sections cover rule-aware taxonomy beside nominals, v1.5.5).

## 9. Ranked gap list, smallest first

Each item names the Protégé feature it unblocks.

1. Metadata and lifecycle (S). Return the real version; honour `getTimeOut`; call the progress monitor at start and stop of classification; throw `ReasonerInterruptedException` when `interrupt()` was called; `isPrecomputed` true only for computed types. Unblocks the Stop button and honest status.
2. Interim safety (S). `isSatisfiable(anonymous)` returns `true` today and `getInverseObjectProperties` claims a property is its own inverse. Both are wrong answers rather than missing ones. Throw `ClassExpressionNotInProfileException` or `UnsupportedOperationException`, or compute, until the real query exists.
3. Inconsistent-ontology behaviour (S). Throw `InconsistentOntologyException` from queries like HermiT; this starts Protégé's inconsistency explanation (8). Decide the `isEntailed` policy against HermiT (5).
4. Fresh named classes and entity policy (S). Synthetic node with Top above and Bottom below; `FreshEntityPolicy.DISALLOW`.
5. Initial classification outside the constructor (M). Needed so Stop works on the first run and so `precomputeInferences` carries the work as in HermiT; keeps plain classification speed if done lazily on first use.
6. Individuals from `--realize` (M): `getTypes`, `getInstances` (named class), `getSameIndividuals`; types CLASS_ASSERTIONS and SAME_INDIVIDUAL. `getTypes` must include Top for unknown individuals. Plan item 1.
7. `getDataPropertyValues` (M but cheap): asserted literals of the property, its sub-properties and the individual's same-individuals, no literal reasoning (HermiT, `R` line 1914). Needs the data property hierarchy (item 9) or a syntactic sub-property closure.
8. Anonymous class expression queries (M/L): `getEquivalentClasses`, `getSubClasses`, `getSuperClasses`, `isSatisfiable`, `getInstances`, `getDisjointClasses` through `Q ≡ CE`. Unblocks the DL Query tab, the DisjointWith and object-property-domain frames, and `getInstances` with expressions. Highest user-visible value after items 1 to 4.
9. Object property hierarchy, inverses, domains, ranges (L): plan `--properties`. Unblocks the three object property views and the inferred property hierarchy. Hierarchy results must use `Role` semantics for inverse expressions (HermiT `H(OWLObjectPropertyExpression)`).
10. Data property hierarchy and domains (L): plan 2.2 (fresh datatype `T`).
11. `isEntailed` for the full axiom list in section 5 (L, in stages): SubClassOf with anonymous sides and Equivalent/Disjoint/DisjointUnion first (class queries), then domain/range, then property characteristics and chains (consistency tests), then assertions, HasKey, DatatypeDefinition. `isEntailmentCheckingSupported` must reflect the stage reached. `isEntailed(Set)` must skip non-logical axioms like HermiT.
12. Object property values, different individuals, disjoint properties (L): on-demand queries in the incremental session; OBJECT_PROPERTY_ASSERTIONS.
13. Datatype facets: length, minLength, maxLength, pattern, langRange, and the facet-per-type table of 6.1 (L, engine). Until then the plugin fails to load ontologies HermiT classifies. Also decide to match HermiT's treatment of non-map datatypes in Protégé (free datatype), which KM already does.
14. SWRL: DataPropertyAtom, DataRangeAtom, complex ClassAtom, DifferentIndividuals atom (L, engine and proofs). Built-ins stay rejected by both.
15. Not needed for parity (KM is ahead or equal): incremental change handling; native explanation for named SubClassOf (HermiT provides no explanations of its own; Protégé's workbench builds them from `isEntailed`).
