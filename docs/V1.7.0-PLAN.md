# KM 1.7.0 plan

Recorded 2026-11-14. The maintainer's goal for v1.7.0:

1. complete for OWL 2 DL;
2. supports in Protégé what HermiT supports;
3. faster and with less memory than every baseline reasoner;
4. certified sound and complete.

Work split: the supervisor designs and validates; agents implement and
prove. Agents never push, merge or run on Ibex.

## 2. One mechanism for every query: fresh definitions

Every OWL API reasoner query reduces to named-class classification of an
extended ontology `O' = O ∪ Δ`, where `Δ` only defines fresh names. This
is how `--realize` already works. It keeps one engine path, one output
format and one certification story: for each query kind, a short Lean
lemma over `OWL.Semantics` states the reduction, and the answer on `O'`
is certified like any classification answer.

Let `B` be one fresh class and, per object property expression `r`
(named properties and their inverses), `P_r` a fresh class.

| Query | Fresh definitions `Δ` | Read-out |
|---|---|---|
| object property hierarchy | `P_r ≡ ∃r.B` for every `r`, `P_⊤ ≡ ∃U.B` | `r ⊑ s` iff `P_r ⊑ P_s`; `r` is empty iff `P_r` is unsatisfiable |
| inverse properties | same | `s` is an inverse of `r` iff `P_{r⁻} ≡ P_s` |
| disjoint object properties | on demand, see 2.1 | |
| domain, range | `Dom_r ≡ ∃r.⊤`, `Ran_r ≡ ∃r⁻.⊤` | named superclasses |
| data property hierarchy | see 2.2 | |
| types, instances | `N_a ≡ {a}` per individual (as `--realize`) | `a : C` iff `N_a ⊑ C` |
| same individuals | same | `N_a ≡ N_b` |
| different individuals | on demand: `X ≡ N_a ⊓ N_b` | `X` unsatisfiable |
| object property values | on demand: `V ≡ ∃r.N_b` | `N_a ⊑ V` |
| data property values | on demand, candidates = literals in `O`: `V ≡ ∃u.{l}` | `N_a ⊑ V` |
| class expression `CE` (DL Query) | `Q ≡ CE` | supers, subs, equivalents, instances of `Q` |
| disjoint classes of `CE` | `Q ≡ CE`, per candidate `D`: `X ≡ Q ⊓ D` | `X` unsatisfiable |
| `isEntailed(axiom)` | per axiom type, reduced to the rows above | |

Correctness of the property row. If `(x,y) ∈ r \ s` in a model, set
`B = {y}`: `x ∈ ∃r.B \ ∃s.B`. If `x ∈ ∃r.B \ ∃s.B`, some `y ∈ B` is an
`r`-successor and not an `s`-successor. `B` is fresh, so both directions
hold for every model of `O`.

Precomputed (one classification each, batched into one run where the user
asks for several): property hierarchy, domains and ranges, types and same
individuals. On demand through the incremental session (`km
incremental`): values, different individuals, disjointness, class
expressions, entailment checks.

### 2.1 Disjoint properties

Disjointness of `r` and `s` has no class form without role conjunction.
It is a consistency test: `r` and `s` are disjoint iff
`O ∪ {r(a,b), s(a,b)}` is inconsistent for fresh individuals `a`, `b`.
km answers it in the incremental session by adding the two assertions.
The same pattern serves `isEntailed` for property-characteristic axioms
that have no class reduction.

### 2.2 Data properties

`u ⊑ v` iff `O ∪ {u(a,l)} ⊨ v(a,l)` for every literal `l`. A fresh
datatype `T` (interpreted freely by the direct semantics) gives the class
form `∃u.T ⊑ ∃v.T`. Whether the frontend and the datatype reasoner treat
an undeclared datatype as free is to be checked first; if not, that
support is the work item.

### 2.3 Engine and plugin interface

- `km classify --properties` adds `SUBPROP`, `EQPROP`, `DOMAIN`, `RANGE`
  rows (JSON keys `"properties"`...), in the manner of `--realize`.
- `km incremental` gains query commands for the on-demand rows.
- The plugin maps every `OWLReasoner` method to these, reports the
  HermiT set of `InferenceType`s as precomputable, and computes each
  lazily on first use so plain classification stays as fast as now.

### 4.1 Procedure for C1 to C3 (decided 2026-11-14)

Facts from the inventory:

- The CB completeness files prove model existence only for a
  caller-supplied finite carrier. Ontologies with inverse roles and
  counting can force infinite models, so a flat finite grounding cannot
  give a total procedure; an unravelling argument is needed in any case.
- No executable CB saturation and no termination theorem exist for the
  production calculus. The hypertableau files (71k lines) are relative to
  producer families that nothing constructs.
- The literature result for the CB calculus is ALCHOIQ+ (Tena Cucala,
  Cuenca Grau, Horrocks, KR 2018); SROIQ is reached through the
  role-chain encoding.
- The v1.6.3 SHI route (7,252 lines) is the one complete pipeline: OWL
  semantics, translation, executable procedure, capstone.

Decision: one new executable reference procedure in the style of the
SROIQ tableau of Horrocks, Kutz and Sattler (2006), built in stages on
the v1.6.3 pipeline, with the standard three proofs per stage:
termination, soundness by unravelling a complete clash-free graph into a
model, completeness by steering the rules with a model.

| Stage | Procedure |
|---|---|
| C1 SHIQ | completion trees, at-least and at-most rules, choose rule, pairwise blocking |
| C2 SHOIQ | completion graphs with nominal nodes, the NN rule, its termination measure |
| C3 SROIQ | regular role chains through the automaton encoding (proved separately, including the regularity check); Self, disjoint, irreflexive, asymmetric roles as extra clash and rule conditions |

The reference procedure defines the exact answer and need not be fast.
km's answers are certified against it where it finishes in the budget,
and by the existing answer checkers elsewhere; the release notes state
the measured coverage, as v1.6.3 did.

Each stage first gets a design note by the supervisor (definitions and
the lemma skeleton), then agents prove it.

### 9.1 C1b: ABox without nominals (design outline)

- **TBox answers do not change.** Without nominals a model of the
  knowledge base and a model of the TBox have a disjoint union, so for a
  consistent knowledge base `EntailsSub (T ∪ A) a b ↔ EntailsSub T a b`.
  One Lean lemma over `OWL.Semantics`; classification of `T ∪ A` is then
  `Inconsistent ∨ TBox answer`.
- **Consistency.** A knowledge base is consistent iff there is an
  *ABox realisation*: a partition of the named individuals (no unique
  name assumption; DifferentIndividuals forbids merges, SameIndividual
  forces them), a type per block, a label per ordered pair of blocks
  that contains the asserted roles and avoids the negated ones, such
  that every block has a list of tree children with good records whose
  star, taken together with the block's ABox neighbours, satisfies
  `StarOK`. Proof: forest model (blocks as roots, unravelled trees
  below), and from a model by reading types, labels and equalities off
  the individuals.
- **Hinted procedure.** Searching all realisations is finite but
  hopeless on large ABoxes. The reference takes an optional hint (a
  realisation, which km exports from its model). It checks the hint with
  the proved checker; a valid hint proves consistency. Without a valid
  hint it falls back to the exhaustive search. Soundness holds for every
  hint; completeness holds for the search. The same pattern certifies
  realization rows (`TYPE a C`): entailed iff `T ∪ A ∪ {a : not C}` has
  no realisation, not entailed iff a hinted realisation shows it.

Cost: the fresh definitions add an inverse role and (through `P_⊤`) a
nominal to every input; six inverse-free inputs go from under a second to

1. Domains are the named superclasses of `P_r` (`B` is fresh, so
   `P_r ⊑ C` iff `∃r.⊤ ⊑ C`); `Dom_r` goes away.
2. `P_⊤` only when the source mentions `owl:topObjectProperty` or a

   individual-free copy, and no named property is universal.
3. An input is *inverse-free* when it has no `ObjectInverseOf`,

## 17. Certification architecture after C1 to C3 (2026-11-15)

The proved reference route `sroiq-c2a` accepts 1,518 of the 1,708 pool inputs at its fragment check. Its exhaustive search is exponential in the number of names and decides nothing of real size. Certification of a km answer therefore splits:

- **Positive rows** (a subsumption, a type, an inconsistency): `kmSupervisor_sound`, as in earlier releases.
- **Negative rows** (a non-subsumption, a non-type, consistency): a model. The proved route accepts a *hint* (a realisation with certificates, text format in `SRIQN/Procedure.lean`, `RawHint.toHintN`) and checks it in time polynomial in the hint. One realisation of a satisfiable class certifies every non-subsumer of that class.

So "certified complete on an input" means: for every negative row km publishes, a hint that the proved checker accepts. The missing piece is the hint producer (item E16). Stage H:

| Step | Content |
|---|---|
| H1 | Hint producer design and prototype: from km's output (class rows, realization rows) and the source, build realisations for every satisfiable class and for the knowledge base; run the proved checker; measure coverage and cost on the pool. |
| H2 | Batch form of the checker: one translation and index per input, many rows. |
| H3 | Release gate: every pool input either certified complete this way, or listed with the reason. |

For TBox-only SHIQ inputs the certified fast route (C1c to C1f) needs no hint.

## 18. Hint-only route (decided 2026-11-15)

`realisation_sound` needs no C2a condition. Certifying a negative km row needs only "the proved checker accepted this model", not completeness of the reference search.
