# KM 1.7.0 plan

Recorded 2026-11-14. The maintainer's goal for v1.7.0:

1. complete for OWL 2 DL;
2. supports in Protégé what HermiT supports;
3. faster and with less memory than every baseline reasoner;
4. certified sound and complete.

Work split: the supervisor designs and validates; agents implement and
prove. Agents never push, merge or run on Ibex.

## 1. Where v1.6.4 stands

| Goal | State at v1.6.4 |
|---|---|
| OWL 2 DL inputs | km accepts OWL 2 DL and classifies named classes. On the 1,708-input pool 1,687 verify; 17 time out, 1 runs out of memory. |
| Protégé | Class hierarchy, equivalents, unsatisfiable classes, consistency, explanations for named subsumptions. Everything else returns empty answers. `km classify --realize` gives individual types and equalities, but the plugin does not call it. |
| Speed and memory | S1 holds against v1.5.3 and Konclude on the held-out half. No current record against HermiT, Pellet/Openllet, FaCT++ and ELK. |
| Certification | Soundness: `kmSupervisor_sound` for every source. Completeness: proved on OWL EL and OWL SHI (`owlReferenceSHI`), through a Lean reference procedure and answer comparison. Not covered: number restrictions, nominals, general role chains, Self, role disjointness and the other role characteristics, datatypes, ABox, DL-safe rules, and every query other than named-class subsumption. |

## 2. One mechanism for every query: fresh definitions

Every OWL API reasoner query reduces to named-class classification of an
extended ontology `O' = O ∪ Δ`, where `Δ` only defines fresh names. This
is how `--realize` already works. It keeps one engine path, one output
format and one certification story: for each query kind, a short Lean
lemma over `OWL.Semantics` states the reduction, and the answer on `O'`
is certified like any classification answer.

Let `B` be one fresh class and, per object property expression `r`
(named properties and their inverses), `P_r` a fresh class.

| Query | Fresh definitions `Δ` | Read-out |
|---|---|---|
| object property hierarchy | `P_r ≡ ∃r.B` for every `r`, `P_⊤ ≡ ∃U.B` | `r ⊑ s` iff `P_r ⊑ P_s`; `r` is empty iff `P_r` is unsatisfiable |
| inverse properties | same | `s` is an inverse of `r` iff `P_{r⁻} ≡ P_s` |
| disjoint object properties | on demand, see 2.1 | |
| domain, range | `Dom_r ≡ ∃r.⊤`, `Ran_r ≡ ∃r⁻.⊤` | named superclasses |
| data property hierarchy | see 2.2 | |
| types, instances | `N_a ≡ {a}` per individual (as `--realize`) | `a : C` iff `N_a ⊑ C` |
| same individuals | same | `N_a ≡ N_b` |
| different individuals | on demand: `X ≡ N_a ⊓ N_b` | `X` unsatisfiable |
| object property values | on demand: `V ≡ ∃r.N_b` | `N_a ⊑ V` |
| data property values | on demand, candidates = literals in `O`: `V ≡ ∃u.{l}` | `N_a ⊑ V` |
| class expression `CE` (DL Query) | `Q ≡ CE` | supers, subs, equivalents, instances of `Q` |
| disjoint classes of `CE` | `Q ≡ CE`, per candidate `D`: `X ≡ Q ⊓ D` | `X` unsatisfiable |
| `isEntailed(axiom)` | per axiom type, reduced to the rows above | |

Correctness of the property row. If `(x,y) ∈ r \ s` in a model, set
`B = {y}`: `x ∈ ∃r.B \ ∃s.B`. If `x ∈ ∃r.B \ ∃s.B`, some `y ∈ B` is an
`r`-successor and not an `s`-successor. `B` is fresh, so both directions
hold for every model of `O`.

Precomputed (one classification each, batched into one run where the user
asks for several): property hierarchy, domains and ranges, types and same
individuals. On demand through the incremental session (`km
incremental`): values, different individuals, disjointness, class
expressions, entailment checks.

### 2.1 Disjoint properties

Disjointness of `r` and `s` has no class form without role conjunction.
It is a consistency test: `r` and `s` are disjoint iff
`O ∪ {r(a,b), s(a,b)}` is inconsistent for fresh individuals `a`, `b`.
km answers it in the incremental session by adding the two assertions.
The same pattern serves `isEntailed` for property-characteristic axioms
that have no class reduction.

### 2.2 Data properties

`u ⊑ v` iff `O ∪ {u(a,l)} ⊨ v(a,l)` for every literal `l`. A fresh
datatype `T` (interpreted freely by the direct semantics) gives the class
form `∃u.T ⊑ ∃v.T`. Whether the frontend and the datatype reasoner treat
an undeclared datatype as free is to be checked first; if not, that
support is the work item.

### 2.3 Engine and plugin interface

- `km classify --properties` adds `SUBPROP`, `EQPROP`, `DOMAIN`, `RANGE`
  rows (JSON keys `"properties"`...), in the manner of `--realize`.
- `km incremental` gains query commands for the on-demand rows.
- The plugin maps every `OWLReasoner` method to these, reports the
  HermiT set of `InferenceType`s as precomputable, and computes each
  lazily on first use so plain classification stays as fast as now.

## 3. HermiT parity list (acceptance for goal 2)

An inventory agent produces `docs/V1.7.0-HERMIT-PARITY.md`: every
`OWLReasoner` method, every `InferenceType`, every `AxiomType` for

## 4. Certified complete for OWL 2 DL (goal 1 and 4)

Method as in v1.6.0 to v1.6.3: a Lean reference procedure, proved to
publish the exact answer on every input of the fragment, with km's answer
compared against it (or km's certificate checked). Completeness theorem
target: `owlReference_complete` on every OWL 2 DL ontology, and the
reduction lemmas of section 2 for the other queries.

Stages, each a usable theorem:

| Stage | Fragment added | Route |
|---|---|---|
| C1 | SHIQ: qualified number restrictions, functionality | extend the SRI normal form with counting clauses; procedure to be designed (4.1) |
| C2 | SHOIQ: nominals; ABox assertions as nominal clauses | |
| C3 | SROIQ: general regular role chains, Self, disjoint, (ir)reflexive, asymmetric roles | Lean proof of the automaton encoding of regular chains (the frontend's encoding), then C2 |
| C4 | datatypes: the OWL 2 datatype map, facets, data ranges | Lean model of the datatype map; a decision procedure for finite conjunctions of data ranges |
| C5 | query reductions of section 2; DL-safe rules | lemmas over `OWL.Semantics` |

### 4.1 Procedure for C1 to C3

Type elimination (v1.6.3) does not extend to counting with inverses and
nominals without a mosaic or integer-programming layer. The Lean
development already formalises the consequence-based calculus that km's
CB engine runs (Sequoia-style, complete for SROIQ in the literature:
Tena Cucala, Cuenca Grau, Horrocks 2018), with soundness and parts of
completeness (`CBSourceEqualityFreeCompleteness`,
`CBNamedGroundCompleteness`). Decision to take after an inventory of
those files: (a) finish CB completeness with equality and nominals plus a
termination proof for an executable Lean saturation, or (b) a
hypertableau with blocking. Default choice: (a), since most of the
soundness side and the equality-free completeness exist.

An inventory agent reports, per CB completeness file: the theorem, its
hypotheses, what clause language it covers, and what is missing for the
full language.

Risk: C2 and C3 are research-size proofs. Each stage ships separately
(v1.6.5 and later) so that v1.7.0 is the release where the last stage
lands.

## 5. Faster and smaller than every baseline (goal 3)

Baselines: Konclude, HermiT, Pellet/Openllet, FaCT++, ELK (EL inputs),
on the 1,708-input pool and on the Protégé query workloads of section 3.
Protocol of the releases: one core, 240 s, 20 GiB, peak memory recorded.
Clauses: km verifies at least every input each baseline verifies; median
and mean wall time and median peak memory no worse than each baseline on
the common inputs; per-query latency in Protégé no worse than HermiT.
Open items today: the 17 timeouts and 1 memory-out, the Konclude mean
(3.6 s against 1.8 s on common held-out inputs, median 0.18 s against
0.16 s), and the cost of the property and individual runs.

## 6. Order of work

1. Plugin: individual types, instances, same individuals from
   `--realize` (small; agent, Sonnet).
2. Engine: `--properties` (object property hierarchy, domains, ranges;
   agent, Opus), tested against HermiT.
3. Inventories: HermiT parity list; CB completeness state; baseline
   numbers (agents, Sonnet, read-only).
4. Design decisions 4.1 and 2.2 from the inventories (supervisor).
5. On-demand queries in `km incremental` and the plugin; differential
   harness.
6. Proof stages C1 to C5; performance lanes from the baseline numbers.
