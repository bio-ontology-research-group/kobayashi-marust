# v1.3 acceptance contract

Version 1.3 adds source-level incremental reasoning and explanations to the
automatic KM reasoner. Passing the existing clause-level tests is necessary,
but it is not sufficient for this release.

## Incremental reasoning

An incremental route must retain algorithm state and perform less work than a
fresh classification for at least one supported addition and one supported
removal or replacement. An exact rebuild remains a permitted fail-safe for a
change that crosses a documented invalidation boundary, but a route for which
every change rebuilds is not incremental.

The source-level session owns the complete flattened OWL ontology. It applies
one atomic OWLAPI change batch, normalises the candidate source with stable
identifiers, selects the automatic route again, and commits only after the
candidate result is complete. Route changes are allowed. A failed update leaves
the prior revision and answer queryable.

Every production mechanism reachable from `KM_ROUTE=auto` needs an explicit
state adapter:

| mechanism | retained state | minimum meaningful update |
|---|---|---|
| ELC and flat-NF1 ELC | completion labels, role edges, normal-form indexes | addition replay and dependency-directed deletion |
| CB, including ordered-resolution variants | contexts, retained clauses, derivation dependencies, messages | insertion saturation and dependency-directed retraction |
| HT ordinary and quasi-order | completed models, probe dependencies, blocking state | model extension and affected-probe invalidation |
| HT cardinality, rules, and native-ABox routes | the corresponding typed source plus completed search/probe state | typed-source update without dropping side metadata |
| automatic router and specialist bridges | source profile, selected route, fallback chain, source identity | route-preserving update or atomic migration to another adapter |

Each adapter must report its route, revision, strategy, retained-state counts,
invalidated-state counts, and whether it migrated to another route. Receipts
must distinguish retained work from an exact rebuild.

For every row above, tests cover addition, removal, replacement, rollback after
a declined update, and a change that alters the automatic route. After every
commit, the incremental classification and supported queries must equal a fresh
`km classify` run over the same complete source. Performance tests must also
show non-zero retained state and a real reduction in route work on at least one
representative transaction.

## OWLAPI and Protege

`KMReasoner` must use one native source-level session rather than spawning a
batch classifier from `handleChanges`. It must implement OWLAPI buffering
semantics:

- `BUFFERING` queues ontology changes until `flush()`;
- `NON_BUFFERING` applies each delivered change batch immediately;
- `getPendingChanges`, `getPendingAxiomAdditions`, and
  `getPendingAxiomRemovals` reflect the unapplied batch;
- imports-closure changes are flattened atomically;
- `interrupt()` cancels the active native request without corrupting the last
  committed revision;
- `dispose()` terminates the native session and unregisters listeners;
- a failed native transaction surfaces as an OWLAPI reasoner error and retains
  the preceding answer.

Tests instantiate both factory modes, modify an ontology through OWLAPI, and
compare every committed hierarchy with a newly constructed KM reasoner. The
same tests run against the packaged Protege bundle, not only loose classes.

## Explanations

Explanations are source-axiom justifications. Every published justification
must contain axioms from the flattened source ontology, entail the requested
inference when checked through the automatic production gate, and be
subset-minimal. Bounded enumeration must state whether more justifications may
exist; the unbounded OWL Explanation API method must either enumerate all
supports or throw without publishing an incomplete set as complete.

The v1.3 OWLAPI surface supports every inference kind that `KMReasoner`
advertises through `isEntailmentCheckingSupported`. Unsupported axiom kinds
throw `UnsupportedEntailmentException`; they never return an empty explanation
set. Explanation queries use the reasoner's committed incremental revision, so
pending buffered changes do not leak into answers and a committed update
invalidates only supports depending on changed source axioms.

Tests cover entailed and non-entailed queries, multiple justifications,
inconsistency and unsatisfiability, annotations and duplicate source
occurrences, imports, cancellation, limits, post-update invalidation, route
migration, and ELC, CB, ordinary HT, cardinality HT, rules, and native-ABox
routes. Every returned OWLAPI `Explanation<OWLAxiom>` is revalidated against
the exact committed flattened ontology.

## Release evidence

The release requires:

1. Rust differential tests for every automatic mechanism in the table.
2. Java OWLAPI lifecycle and explanation-interface tests.
3. A packaged Protege installation smoke test with the native v1.3 binary.
4. No regression in the v1.2 certified batch classification corpus.
5. Documentation of supported inference kinds and every exact-rebuild
   boundary that remains as a safety fallback.
