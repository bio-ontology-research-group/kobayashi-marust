# HermiT parity scoreboard for the KM Protégé plugin

Ontologies: 42. Method-ontology cells where HermiT answered or failed: 1795 (42 further cells left out because HermiT timed out or never reached them). Reasoner calls compared: 122693.

**Parity score (strict): 55.4%** (994 of 1795 cells). Lenient score, where a node grouping difference with the same entities does not count: 55.5% (997 of 1795). Adjusted score, which also ignores differences that consist only of owl:Thing or owl:Nothing (or the top and bottom properties) appearing in one answer and not the other: 58.6% (1051 of 1795).

Splitting each method by the kind of argument (named entity, anonymous class expression, top or bottom entity, inverse property expression) gives 2956 cells and a strict score of **56.8%** (1679 cells), adjusted 65.3% (1930 cells).

A cell is one OWLReasoner method on one ontology; it counts for KM when KM agrees with HermiT on every call of that method (HermiT errors that KM answers are not held against KM), or when HermiT fails on the whole cell and KM answers. Settings: HermiT 1.4.3.456 with `ignoreUnsupportedDatatypes = true`, KM plugin through the OWL API 4.5.29, `KM_THREADS=1`.

## Run settings and ontologies

- Date 2026-11-14. Harness `protege-parity/` on branch `v170/differential-harness` (development/v1.7.0 plus the harness; the plugin is unchanged). Plugin 1.6.4 build, OWL API 4.5.29, HermiT 1.4.3.456 (Protégé's configuration, `ignoreUnsupportedDatatypes = true`), km `scratch/w2p/km` (with `--realize` and `--properties`), `KM_THREADS=1`, one ontology at a time, Java 21.
- Time limits: 180 s of wall time per reasoner per ontology (the harness default is 120 s) and 20 s for a single query after precompute; the four ontologies KM did not finish within 180 s (ore_ont_5841, ore_ont_8273, ore_ont_9662, ore_ont_13700) were rerun with 600 s, and the raw JSON holds the 600 s runs (the 180 s runs are kept in `out-180/`). A reasoner past its limit is stopped and the calls it did not reach count as timeouts. HermiT hit its limit on 13 ontologies in the 180 s runs (and on 4 of them again at 600 s), always in the late phases (anonymous class expressions, disjoint queries; on ore_ont_13700 a query did not return after interrupt), so its cells for those phases are partly missing, not failed; cells with no HermiT answer are left out of the score.
- Sampling: seed 1, up to 200 entities per kind, 16 generated anonymous class expressions, up to 5 axioms per axiom type for `isEntailed`; see the README for the rest.
- Ontologies: 40 from the v150 corpus (under 2 MB, 30 KB and up, 10 or more classes, chosen with the census by `select_ontologies.py`, seed 170): EL 7, ALC 2 (only two ALC inputs fit the size window), SHI 6, SHIQ 6, SHIQ+ABox 7, SHOIQ 7, SROIQ 5; 21 have individuals, 31 data properties, 31 inverse roles. Plus the W3C wine and food ontologies. Duplicates in the corpus: ore_ont_3987 and ore_ont_4936 have the same signature and size.
- KM did not classify 6 ontologies: four refuse the input (ore_ont_2526, ore_ont_7532, ore_ont_8250, ore_ont_9662; see "Ontologies KM refuses"; ore_ont_9662 and ore_ont_7532 only after minutes of work), two ran past 600 s (ore_ont_8273, ore_ont_13700) where HermiT finished the class hierarchy in under 40 s. A seventh, ore_ont_5841, needs about 180 s of precompute and completed on the 600 s rerun. These ontologies contribute KM-unsupported or KM-timeout cells and pull the score down; the per-ontology table shows the score on each.
- ore_ont_5014 is inconsistent (both reasoners agree); nearly all its calls are both-throw-the-same-exception agreements.

## Reading the result

- Where KM answers, it agrees with HermiT on the named class hierarchy and the object property hierarchy once `owl:Nothing` conventions are set aside: adjusted score 88% for `getSubClasses`, `getSuperClasses`, `getEquivalentClasses` and `isSatisfiable` on named classes, 85% for the object property methods. The missing cells there are the ontologies KM could not classify.
- The parity gaps are concentrated in: anonymous class expressions (empty answers and a refused `isSatisfiable`), the data property hierarchy and data property domains, object and data property values, disjoint classes and properties, different individuals, `isEntailed` for most axiom types, `getPrecomputableInferenceTypes`, and ontologies KM refuses or does not classify within the limit.
- Empty answers where HermiT has facts are not exceptions: the plugin returns an empty set for the queries it does not implement (`getObjectPropertyValues`, `getDataPropertyValues`, `getDataPropertyDomains`, the data property hierarchy, `getDisjoint*`, `getDifferentIndividuals`, anonymous expressions). A client cannot tell this from a true empty answer; the adjudication section lists them as KM wrong.
- A KM classification that fails is retried on every later call (about the cost of one run per query), so a refused ontology also looks like a hang to a caller.

Call verdicts, all calls: agree 77039, both_error_different 40, both_error_same 2584, both_failed 8, differ_content 15579, differ_structure 39, hermit_error 12, hermit_timeout 1209, km_timeout 22815, km_unsupported 3368.

## What the harness does not cover

- Ontology edits. Every run loads the ontology once and queries it. `flush`, buffering, pending changes after an edit, incremental updates and the reasoner state after a failed run are not exercised (`getPending*` and `flush` are asked on an idle reasoner).
- Interruption and limits. `interrupt()` is only called idle or after a query ran past the per-call cap; progress monitor calls, `TimeOutException` from a configured timeout and Protégé's Stop button are not tested. The worker kill is the only hard limit.
- Configuration variants. One HermiT configuration (Protégé's, `ignoreUnsupportedDatatypes = true`), the default fresh entity policy and the default individual node set policy. `BY_SAME_AS`, `THROW_EXCEPTION` and the timeout are not varied.
- Protégé itself. No Protégé window, preference mapping, explanation workbench or DL Query tab. The harness checks the `OWLReasoner` answers those features read, not the features.
- Query shapes outside the plan: queries on anonymous individuals, data range class expressions with facets in `getInstances`, SWRL rules, keys, imports other than the W3C wine and food pair, and axioms the generator has no template for (keys, datatype definitions, annotation axioms beyond those in the ontology).
- Sampling. At most 200 entities per kind, 6 for the disjoint and different-individual queries, 30 property expressions for domains and ranges, 40 individuals by 15 properties for values, 5 axioms per axiom type. One seed (1). A difference outside the sample is not seen; the counts in the difference tables are counts of sampled calls, not of ontology facts.
- Correctness of HermiT. The harness is differential. Where both agree it does not know they are right; where they differ the adjudication section decides by hand on a sample, and not every shape has a source check.
- Scale and speed. Ontologies under 2 MB, one run per reasoner, one machine, `KM_THREADS=1`, a time limit that ended several runs, no repeats. Phase times are indicative only.
- The Protégé 6 build (OWL API 5) is not run; the module builds against OWL API 4.5.29 and HermiT 1.4.3.456.
