# KM v1.6.0: the completeness proof

Started 2026-11-09 on `development/v1.6.0` from the v1.5.5 release merge
(4bcee479). The roadmap row reads: "Prove completeness. Replace the assumed
completeness fields with proofs for each procedure on its fragment,
instantiate the supervisor, and cover the routing to those procedures."
This document fixes what that sentence means as a theorem, why the obvious
reading is not provable, and how the proof is built.

## 1. What is assumed today

`KMConcreteAutomaticSupervisor.ConcreteSupervisor` has two fields,
`selectedComplete` and `fallbackComplete`, each of the form

    (execute route).worker.CompleteAt source

where `SourceBoundWorker.CompleteAt worker source` says the worker's `run`
function returns `.publish`. `run` stands for a Rust process. Nothing in
Lean can prove that a Rust process publishes, so the fields are
hypotheses, the structure has no instance, and the capstone
`ConcreteSupervisor.sound_and_complete` is conditional on them. The
2026-10-27 audit (`docs/history/LEAN-BOUNDARY-AUDIT-2026-10-27.md`, section
1.4) records this.

The calculi themselves have completeness theorems at the level of their
closure relations: `ELCompletion.subsumption_complete` (the EL completion
closure derives every entailed named subsumption), the propositional and
clause-level resolution completeness (`CompletenessProp`,
`CompletenessClause`), the equality-free CB canonical model
(`CBSourceEqualityFreeCompleteness`), and the hypertableau decision
totality theorems (`HypertableauRegularDecisionTotal`,
`HypertableauProductionDecisionTotal`), which are relative to a producer
type that Rust is expected to inhabit. None of these is connected to the
supervisor, because the supervisor's notion of completeness is "the
process publishes", not "the closure contains the answer".

## 2. The theorem that can be proved

Replace "the Rust process publishes" by "a Lean procedure publishes, and
the supervisor runs it". Concretely:

1. A **reference procedure** for a fragment F is an executable Lean
   function `ref : RoutingSource → Outcome (Publication …)` with three
   theorems: it publishes on every source in F (totality), every
   publication names the routed source (source exactness), and every
   publication is accepted by the Lean checker `requestedExactAccept`
   (acceptance). Acceptance gives soundness through the existing
   `requestedExactAccept_sound`; totality and acceptance together give
   `CompleteAt` on F as a theorem.

2. The **supervisor instance** composes every route's Rust execution with
   the reference procedures as the last stage: the Rust worker runs first,
   and when it defers, errors or times out, the reference procedure for
   the source's fragment runs. In Lean, `execute route :=
   (rust route).orElse ref`. The Rust execution is a parameter of the
   instance, constrained only by the fail-closed contract already in
   `KMRequestedExecution` (its publications are source-exact and
   checker-accepted). Nothing about the Rust worker's behaviour on a
   source is assumed.

3. The **capstone** quantifies over every router decision and every
   fail-closed Rust executor:

       theorem kmSupervisor_complete_on_EL (rust) (decide) :
         CompleteOn RequestedCorrect ELFragment (kmSupervisor rust decide).run

   together with unconditional soundness. Routing is covered in the
   strongest sense: whichever route the selector and its fallback choose,
   the supervisor publishes a correct answer on the fragment. This also
   removes the need to prove that Rust's profile predicates agree with
   Lean's `select`, because the theorem holds for every `decide`.

4. The **Rust change** that makes the theorem describe the shipped
   system: the automatic supervisor gains a terminal stage that runs the
   Lean reference binaries after every exact route has declined. Each
   binary declines in constant time when its recogniser does not accept
   the source. A gate test forces every Rust route to decline and checks
   that the reference stage publishes the right answer.

What the theorem says and does not say:

* It is completeness of the idealised procedure: the Lean function has no
  resource bound. A Rust process running the same function can run out
  of time or memory; the model represents that as `.timeout`, which the
  fail-closed design turns into "no answer", never into a wrong answer.
  The release claim is therefore "sound, and complete up to resource
  exhaustion, on F".
* The fragment F is defined on the common clause source `List FCL`, the
  frontend's normalised clause stream. The frontend itself (OWL parsing,
  IRI identity, normalisation) stays outside the boundary, as the roadmap
  assigns it to the frontend proof.
* Completeness of the reference procedure is a theorem about its
  closure, not about the certificate language of the Rust worker. Whether
  the Rust ELC worker's V5 certificate can express every EL answer
  (checker completeness) is a separate, useful statement left for later;
  it does not affect the capstone because the reference, not the
  certificate, carries coverage.

## 3. Fragments and procedures

The routing selector (`KMAutomaticRouting.select`) sends a source to one
of 21 routes; `automaticFallback` adds the exact fallback for the atomic
specialists. The routes group into four coverage families:

| family | routes | reference procedure | status |
|---|---|---|---|
| EL completion | `elc`, the EL arm of `certifiedElProduction` and `productionAll*` | executable EL completion on NF1 to NF7 plus reflexive roles, read from the FCL source by a recogniser | phase 1, this release |
| ALC-shaped sources (disjunctive GCIs, existential and universal restrictions, no role axioms) | the non-EL part of `productionAll*`, `cbPlain*`, `htGeneral` on such sources | computable finite type elimination: `CompletenessStrategy.saturate` already decides subsumption exactly (`saturate_decides`, `engine_complete`) and `CBALCEncoding` ties the ALC clause language to the common source (`entailsSub_iff_good`); the open steps are a computable twin of `saturate`, a recogniser inverting `CBALCEncoding.encode`, and the adapter | phase 2, this release |
| regular hypertableau (equality-free, with role hierarchies, inverses, chains) | `htGeneral`, HT members of the portfolios | the `HypertableauRegularDecisionTotal` theorems are total relative to a `CheckedRegularControlProducer`, but nothing in `lean/` constructs a producer executably; the `frontierAddress` obligation of `ConstructedRegularFiniteSearchFamily` is the crux, and a taxonomy needs 1 + n + n² global decisions | deferred; the survey (`docs/history/SURVEY-HT-CB-COMPLETENESS-2026-11-09.md`) estimates 2,000 or more lines of new executable search |
| CB total calculus | `nominals`, `cbPlain*`, `cbAbsorb*`, `lean`, `seqOn/Off`, CB members of the portfolios | every CB completeness theorem is conditional on supplied data (clash-free terminal saturation, finite carrier); `CBSourceEqualityCanonicalModel` stops before "the quotient satisfies every source instance"; no executable CB saturation and no production termination theorem exist (`Termination.lean` bounds core counts only) | phase 3, research scale |
| rules | `htRules` | rule tableau completeness is not proved; no fallback by design | out of scope for v1.6.0 |

The checkers-on suite of 2026-10-30 (1,781 inputs) routed 593 to `elc`,
542 to `production_all`, 252 to `certified_nominals`, 188 to `ht_bridge`,
105 to `ht_rules`. Phase 1 therefore covers the single largest route and
the EL part of the portfolio routes.

## 4. Phase 1: EL

### 4.1 Lean modules

* `ELCompletionRelativeRefinement.lean`. The existing
  `ELCompletionRefinement.ClosedState` quantifies over every concept name,
  which an executable materialisation over a finite universe cannot
  satisfy. `ClosedStateOn U` restricts the closure obligations to contexts
  in `U` and requires `U` to contain every nf3 filler. The theorems
  `ClosedStateOn.sub_complete`, `edge_complete`,
  `entails_iff_materialized_on` and `unsat_iff_materialized_on` are the
  relative versions of the existing ones, proved by the same mutual
  induction with the invariant that edge targets stay in `U`.

* `ELReferenceSaturation.lean`. Executable closure: the universe is
  `top`, `bottom`, the requested named concepts and every concept of the
  ontology; the state is a duplicate-free list of label facts and edge
  facts; one step adds every rule consequence; `saturate` iterates with
  fuel equal to the size of the fact universe plus one and stops at the
  first fixpoint. Theorems: the result is `ClosedStateOn universe` (a
  fixpoint contains every consequence; a fixpoint is reached within the
  fuel by pigeonhole on the fact universe) and `SoundState` (every added
  fact has a derivation). `referenceAnswer` reads the matrix out and
  `referenceAnswer_exact` gives each bit as `EntailsSub` through
  `entails_iff_materialized_on`.

* `ELCommonSourceRecognizer.lean`. `recognizeEL : List FCL → Option
  RecognizedEL` classifies every clause of the common source as a top
  clause, an nf5 or bottom clause, nf1, nf2, nf4, nf6, nf7, a reflexive
  role, or one half of an nf3 pair (role half and filler half sharing one
  function symbol and one subject), and fails closed on anything else.
  Top and bottom are fresh names when the source has no total or empty
  concept clause; the fresh names are conservative for every subsumption
  between source concepts. The theorem `recognizeEL_entails_iff` states
  `Entails L sub sup ↔ ELCompletion.EntailsSub O sub sup` for every
  source concept pair, proved by model transport in both directions
  (`interpOfModel` and `modelOfNormalAndRaw` in
  `ELNormalCheckerTermEmbedding` already do most of it; the recogniser's
  function symbols are an injective renaming of the canonical slot
  codes, as in `CBSourceWire.renameOntology`).

* `KMConcreteWorkerAdapters.lean`. New evidence constructor
  `KMExactEvidence.elReference`; `elReferenceAccept` recomputes the
  reference answer for the source and compares; `elReferenceAccept_sound`
  from `referenceAnswer_exact` and `recognizeEL_entails_iff`.
  `elReferenceExecution : KMRequestedExecution` publishes the reference
  answer when the recogniser accepts and the named list is duplicate-free,
  and defers otherwise; `elReferenceExecution_completeAt`.
  `KMRequestedExecution.orElse` composes two executions fail-closed.

* `KMAutomaticSupervisor.lean`, `KMConcreteAutomaticSupervisor.lean`. The
  structures lose the two completeness fields. Coverage becomes a
  predicate `CoversAt source` (some route of the execution plan is
  complete at the source); `completeAt`, `complete_on` and
  `sound_and_complete` take it as a hypothesis. Soundness stays
  unconditional.

* `KMSupervisorInstance.lean`. `kmExecute rust route := (rust
  route).orElse elReferenceExecution`, `kmSupervisor rust decide`,
  `ELFragment`, and the capstone theorems `kmSupervisor_sound`,
  `kmSupervisor_complete_on_EL`, `kmSupervisor_sound_and_complete_on_EL`.
  The routing gate audits them with `#print axioms`.

### 4.2 Rust and the gate

* Lean executable `km-el-reference`: reads the frontend's normalised
  clause stream and the requested class list, maps it to `List FCL`
  exactly as the existing checkers do, runs `elReferenceExecution`, and
  prints the taxonomy or declines with exit code 3.
* `engine/src/orchestrate`: after the selected route and its exact
  fallback have declined, the automatic supervisor runs the reference
  stage (`KM_REFERENCE_STAGE=0` disables it). The published answer is
  checked by `requestedExactAccept` in the binary itself, so the Rust
  side only parses.
* Gate: `lean/run-routing-certification-gate.sh` audits the new theorem
  names; a Rust test forces every route to decline on an EL fixture and
  checks that the reference stage publishes the HermiT answer; the
  checkers-on suite records `reference` events.

### 4.3 Acceptance

`docs/V1.6.0-ACCEPTANCE.md` lists the clauses. In short: the capstone
theorems exist, are `sorry`-free and depend only on `propext`,
`Classical.choice` and `Quot.sound`; the reference stage publishes on
every EL input of the suite when the exact routes are forced to decline;
no answer changes anywhere; the speed clauses of v1.5.5 hold again.

## 5. Phases 2 and 3

The survey of 2026-11-09 (`docs/history/SURVEY-HT-CB-COMPLETENESS-2026-11-09.md`) settled the phase
2 choice. The hypertableau totality theorems are relative to a producer
that nothing constructs executably, and building one is a large new search
with an unproved blocker obligation. The ALC type-level argument, by
contrast, is finished and hypothesis-free: `CompletenessStrategy.saturate`
eliminates from the consistent types of the finite concept signature to the
greatest self-realising set, `saturate_decides` states exact subsumption,
and `CBALCEncoding` connects the ALC clause language (`Ctx.Clause`:
disjunctive GCIs, `a ⊑ ∃r.b`, `∃r.d ⊑ c`, `a ⊑ ∀r.b`) to the common
source. Phase 2 therefore adds a second reference procedure by the same
pattern as EL:

* `ALCReferenceSaturation.lean`: a computable twin of `saturate` (decidable
  instances for `consistent`, `compat`, `realizedIn`; the same `Finset`
  definitions without classical choice) with `saturateC = saturate`, and
  the readout bit with its exactness theorem from `saturate_decides`.
* `ALCCommonSourceRecognizer.lean`: `recognizeALC` inverting
  `CBALCEncoding.encode` up to function-symbol renaming, variable renaming
  and clause order, with the entailment equivalence from
  `CBALCEncoding.entailsSub_iff_good`.
* The adapter (`alcReference` evidence and execution) and the instance:
  `kmExecute rust route := ((rust route).orElse elReferenceExecution).orElse
  alcReferenceExecution`, with `kmSupervisor_complete_on_ALC` and the
  union fragment theorem.

Type elimination enumerates the consistent subsets of the concept
signature, so the ALC reference is exponential and runs in practice only
on small sources; it is the completeness witness, not a worker. The
release notes say so.

Phase 3 (CB) is the full calculus: executable saturation, termination, and
the canonical model with equality, nominals and role chains. The survey
puts it at research scale (the equality canonical model lacks its final
theorem, nothing executable exists, and arbitrary role chains may not even
be decidable without the regularity condition the frontend enforces). The
plan records it so that the release notes can say exactly which fragments
are covered and which are not. The HT producer remains the alternative
for role hierarchies, inverses and chains after v1.6.0.
