# Stage C1b: SHIQ knowledge bases with an ABox (design)

Supervisor's design note, 2026-11-14. Normal-form level, on top of
`lean/ContextCalculus/SRIQ` (stars, `Good`, `classifyQ`). The census puts
431 pool inputs behind this stage.

## 1. Normal form

New files under `lean/ContextCalculus/SRIQ/` (`ABox.lean`,
`ABoxProcedure.lean`, tests). An ABox over individuals `Ind`:

```
inductive Assertion (CName Role Ind)
  | cls (a : Ind) (A : CName)                  -- A(a)
  | role (a : Ind) (R : RoleT Role) (b : Ind)  -- R(a,b)
  | nrole (a : Ind) (R : RoleT Role) (b : Ind) -- not R(a,b)
  | same (a b : Ind) | diff (a b : Ind)
```

A knowledge base is a pair `(O, A)` of a `SRIQ.Ontology` and a list of
assertions. An interpretation is a `SRI.Interp` with `ind : Ind → D`. No
unique name assumption. Complex and negated class assertions arrive as
names through the translation (`A(a)` with `A` a definition name).

`ConsistentKB O A`: some interpretation over a nonempty domain models
`O` and satisfies `A`. `EntailsSubKB O A a b`: every such interpretation
has `a ⊑ b`.

## 2. The TBox answer does not change

`entailsSubKB_iff`: `EntailsSubKB O A a b ↔ ¬ ConsistentKB O A ∨ EntailsSub O a b`,
for every ontology `O` (no restriction on chains). Right to left is
immediate. Left to right, given a model `I` of the knowledge base and a
model `J` of `O` with an element in `a` and not in `b`, the disjoint sum
`I ⊕ J` with `ind` from `I` models both: every clause kind is local to a
component (paths, successor lists and counts stay inside one summand).

## 3. Realisations

Fix `O` with `IsALCHIQ O`. A realisation consists of

- a type `B` of blocks and `blk : Ind → B`;
- `ty : B → Finset CName`;
- `lab : B → B → Finset (RoleT Role)`, up-closed, with
  `lab c b = flipL (lab b c)`;

such that

- assertions hold: `cls a A → A ∈ ty (blk a)`; `role a R b → R ∈ lab (blk a) (blk b)`;
  `nrole a R b → R ∉ lab (blk a) (blk b)`; `same a b → blk a = blk b`;
  `diff a b → blk a ≠ blk b`;
- every block `b` has a list `C` of tree children with
  `StarOK O (ty b) (N b ++ C)` and `Good O (s, some (flipL L, ty b))` for
  each child `(L, s)`, where `N b` lists `(lab b c, ty c)` for the blocks
  `c` (including `b` itself) with `lab b c ≠ ∅`, one entry per block.

`consistentKB_iff_realisation`: for finite `Ind` (and the finiteness the
star theorem needs), `ConsistentKB O A ↔` a realisation exists with
`B` finite (a quotient or subtype of `Ind`).

- **From a model.** Blocks are the values `I.ind a`; `ty` and `lab` are
  read off. Children of a block: the star construction of
  `Stars.type_good`, with witnesses that are named elements removed
  (they are in `N b`). Counting works as there: the entries counted are
  distinct elements.
- **To a model.** A forest: the blocks, plus below each block the
  unravelled trees of its children (generalise `unravel_models`: roots
  are block children instead of one root record). Roles between blocks
  from `lab`, between a block and its tree children and inside trees as
  in the unravelling. Neighbours of a block are exactly `N b ++ C`;
  neighbours of a tree node are its star.

## 4. Transitivity

`encTransQ` applies to the TBox; assertions pass through. Correctness
with an ABox needs the two model maps of `encTransQ_correct` to preserve
assertions: positive ones are preserved in both directions; a negative
role assertion is preserved when its role is simple. So `IsSHIQKB`
requires `IsSHIQ O` and simple roles in `nrole` assertions (OWL inputs
that violate it are declined, with the reason).

## 5. Procedure with a hint

Over `Fin n`, `Fin m`, `Fin k`:

- `checkRealisation O A ρ : Bool` for a concrete finite realisation `ρ`
  with explicit children lists, using `alive` for goodness. Sound:
  `true` implies `ConsistentKB`.
- `searchKB O A : Bool`: decides `∃ ρ` over the finite space (block maps,
  types, labels, children up to the bound of `support_bound`), for
  example by `decide` on a `Fintype`. Exact, and far too slow for real
  inputs; it defines the answer.
- `consistentKB O A (hint : Option ...) : Bool`: `true` if the hint
  checks, else `searchKB`. Theorem: equals `ConsistentKB` for every hint.
- `classifyKB`: if consistent then `classifyQ` rows, else every requested
  name is unsatisfiable; spec against `EntailsSubKB`.

km will export the hint from its model (block map, types, labels,
children) in a later engine step.

## 6. Realization rows (next step, not this brief)

`O, A ⊨ C(a)` iff `(O, A ∪ {nC(a)})` is inconsistent, with `nC` the
complement name; non-entailment is certified by a hinted realisation.
